Design Review — Versioned Databases & Backups

Source snapshot: workspace (1), commit b9b40a7. Section 1 describes existing code; sections 2-6 specify proposed changes, not implemented features. The live Turso OpenAPI contract was read for this revision. No authenticated provisioning or restore operation was executed.

Purpose. A context/design document proposes: (1) versioned Turso databases named wod-wiki-{version}, with the version stored in localStorage (playground) and .env (CLI/self-hosted); (2) scope reduction so sync carries only user data, filtering seedOrigin === 'seed' rows and seed-only stores at journal/snapshot time; (3) db-to-db migration reusing applySyncBatch idempotency, a publishCatalogSeed round-trip, and the extracted migrateRemoteToCurrent scratch chain; (4) backing up older versions; (5) an implementation file map with open questions. This review assesses each proposal against the code as it exists today, lists the changes required to make the design sound, and catalogs pitfalls in the existing design that the plan will inherit or must defuse.

1. How things work today (verified)

1.1 Data plane and sync protocol

  • The browser data plane is IndexedDB via IndexedDBStorage.ts over STORE_DEFS; the schema version is DB_VERSION = 31 (packages/storage/src/schema.ts:19). The system-flagged memberships store survives wipe and is excluded from snapshots and remote applies. Browser-local sync_outbox/sync_state stores sit outside STORE_DEFS and never enter those payloads.
  • Backup/sync is an op log in three Turso tables: _wodwiki_sync_ops, _wodwiki_sync_state, _wodwiki_sync_ops_archive (packages/storage/src/sql/sync.ts:43-47). A mutation is one of put | delete | clear | wipe against an IndexedDB store/key (sync.ts:50-54).
  • applySyncBatch (sync.ts:277) is idempotent by client-generated group id: presence of {entry.id}:0 skips the whole group, and inserts use ON CONFLICT ("op_id") DO NOTHING. rev is a target-local monotone counter assigned at insert time; at (client ms timestamp) is stored but never consulted for ordering.
  • fetchSyncOps (sync.ts:338) replays ops with rev > afterRev in (rev, idx) order, in whole revision groups. On the client, IndexedDBStorage.applySyncMutations (IndexedDBStorage.ts:413) applies ordered mutations with note/revision guards, then replays pending outbox groups on top. This overlay protects only unshipped writes; acknowledged groups are removed and cannot protect later local edits from restored old payloads.
  • replaceSyncLog (packages/storage/src/sql/sync.ts:380-409) archives the active log, clears it, and writes converted snapshot groups at rev 1..n with the schema marker in one transaction. This mutates the existing database. The archive preserves old op payloads, not a separately frozen database or the old schema marker; it is not a whole-database backup.
  • TursoSyncEngine uses profile-local Web Locks, not a cross-device migration lock. Target state keys use fnv1a(url): cursor:, watermark:, and bootstrapped: (syncEngine.ts:284-287). Bootstrap groups use a persisted browser UUID and a sequence restarted for each snapshot, bs:{bootstrapId}:{seq} (syncEngine.ts:446-503). Different browser UUIDs do not normally collide; reusing one UUID for changed snapshots against retained or copied history is the risk. Migration groups use migrate:{uuid} (syncEngine.ts:400-403).
  • probeSyncTarget classifies targets as empty | unknown | legacy | current. Unknown and newer-schema targets halt. Older targets are currently migrated in place by migrateRemoteToCurrent, using scratch IndexedDB at the remote schema version and then replaceSyncLog (syncEngine.ts:291-413). Schema versions below v20 are refused (syncEngine.ts:351-356). The scratch name is fixed; extraction must isolate each run and clean up abandoned scratch state.

1.2 Config plumbing

  • Browser settings use localStorage key wodwiki.dataSettings.v1 with { kind: 'turso', url, authToken } or { kind: 'indexed-db' } (dataSettings.ts:47,155-188). Validation allows secure libsql/HTTPS/WSS and loopback HTTP/WS, rejects embedded credentials/query/fragment, and proves INSERT permission with a rolled-back write. It does not verify the token's scope, tenant identity, or that the database is safe to adopt. Tokens are stored in plaintext browser storage. There is no default remote URL.
  • CLI/dev server: resolveDatabaseConfig (packages/tools/src/cli/config.ts:319-374) resolves flags > process env > .env. Relevant vars: DB_DRIVER, DATABASE_URL, TURSO_DATABASE_URL, TURSO_AUTH_TOKEN, LIBSQL_AUTH_TOKEN, WOD_WIKI_DB, SQLITE_PATH. Conflicting selectors fail closed; provisioning must preserve that precedence.
  • No Turso Control API usage exists anywhere in the tree — no database create/delete, no token minting. Provisioning is entirely manual today.

1.3 Seed pipeline and membership

  • publishCatalogSeed reads SQL domain notes and their block index/effort/equipment rows, then writes seed manifests/chunks (packages/tools/src/cli/publish.ts:27-160). It is a catalog publication path, not a complete backup format. The seed contract is SEED_SCHEMA = 9 (packages/tools/src/seedbuild/contract.ts:4).
  • Seed import stamps notes with seedOrigin, seedVersion, seedChunkId, and sourceId (packages/engine/src/seed/runtime.ts:305). Related rows do not share one origin flag: block projections use isStatic, definitions use registrySource, and revisions/links can lack either. Import writes checkpoints under meta/seed:{sourceId} and skips existing user-owned notes (runtime.ts:232-263,283-380).
  • Membership: a single local membership default owns every user-created record; adapters stamp userId on write via stampUserOwned, which passes seed rows through untouched (packages/storage/src/membership.ts). USER_OWNED_STORES lists 14 stores; field_* stores, meta, and memberships are excluded from ownership.
  • The meta store is not seed-only: besides seed:{sourceId} checkpoints it carries remote-mode prefs (wodwiki.routeWql.v1, notebooks, telemetry) (metaStore.ts:17-23).

1.4 Two channels, one database (the fact the plan must reckon with)

  • The only consumer of the op-log protocol (applySyncBatch, fetchSyncOps, replaceSyncLog, readRawSyncOps) is the playground sync engine. Verified by tree-wide search: no CLI or server code touches _wodwiki_sync_*.
  • The CLI and self-hosted server write STORE_DEFS-derived domain tables and SQL projections, maintained by refreshDomain (packages/storage/src/sql/domain.ts:246). Those tables are distinct from the browser backup op log; a shared hostname does not make the two write paths interoperable.
  • Consequence: a browser-only backup database contains only _wodwiki_sync_* tables — no domain tables. A CLI-initialized database contains domain tables and a _wodwiki_schema guard, which the sync engine probes as legacy and imports through the scratch chain. The two channels never write each other's tables; nothing reconciles them.

3. Detailed review and required changes

3.1 Versioned databases and the fork key

Finding. App release, storage compatibility, and seed artifact format are separate versions. The existing sync protocol enforces DB_VERSION = 31; SEED_SCHEMA = 9 validates manifests. Neither a new app release nor a seed-only format change proves that stored user records require migration. V30 also shows that DB_VERSION can change for browser-local infrastructure without changing domain rows (schema.ts:9-19).

Required changes.

  • Use the existing storage compatibility key, currently DB_VERSION, for live target naming, for example wod-wiki-v31. Do not add a speculative seedEpoch to the fork key. If a seed change alters user-record identities or references, migrate those records explicitly under the storage compatibility contract.
  • App releases reuse the compatible live database. Optional release archives are copies with unique snapshot identifiers, not new live targets. A restored or forked database needs its own identity even when its schema matches; schema version is not a history generation.
  • The existing migration floor is v20 (syncEngine.ts:351-356). Below that, preserve the archive and require a verified intermediate converter. Do not promise restore support merely because an old database or old app build still exists.

3.2 Write/create paths and provisioning

Finding. No provisioning implementation exists. The browser accepts a pasted token and proves write permission, not token scope (dataSettings.ts:123-165). Management credentials must stay in trusted CLI/server code regardless of CORS. The live specification establishes API shapes, not account eligibility or tested backup guarantees.

Control API correction. The current Turso OpenAPI specification defines database create/delete, database-scoped token generation, and usage reads under /v1/organizations/{organizationSlug}/databases. Create accepts seed.type = database with an existing database name and optional recovery timestamp. The documented recovery window is 24 hours, or 30 days on the scaler plan. In contrast, POST /v3/organizations/{organizationId}/databases/{databaseId}/restore recovers a database deleted within five days, at its deletion state. It requires a paid plan, admin/owner access, and organization recovery enabled. Do not describe that endpoint as arbitrary snapshot restore. Database tokens default to full access and no expiry; choose authorization and expiry explicitly. Verify actual plan limits, recovery eligibility, and token retirement behavior before shipping.

Required changes.

  • Provision through the CLI. Any future wod db create command is proposed, not available today. Mint only database-scoped client credentials; never print them by default or put them in URLs, logs, or shell arguments. Require explicit pairing/export. Make .env writes opt-in, atomic, owner-readable only, preserving unrelated settings and refusing silent credential replacement. A failed config write must not switch targets or automatically delete the created database.
  • Use the hostname/URL returned by provisioning; do not synthesize it from a database name or organization slug. Apply the browser's transport and credential-placement rules, then probe identity/schema separately. A name prefix and a successful INSERT are not ownership proof.
  • Keep browser backup targets separate from live CLI/server domain databases. An explicitly requested one-way export may materialize into an isolated domain database. It does not enable shared live writes; bidirectional reconciliation is outside this design.

3.3 Backing up older versions

Finding. Versioned names do not preserve old versions if the browser still runs its automatic in-place migration. ensureReconciled currently converts an older target and replaces its active log (syncEngine.ts:321-330,404-410). Whole-database retention requires a deliberate copy-before-cutover path and preventing old clients from continuing writes to the archived source.

Required changes.

  • Freeze source writers before the final copy, retain the source and its schema marker unchanged, convert into a new target, validate restoration, then switch settings. Revoke or rotate old write credentials across devices; a localStorage reload guard reaches only sibling tabs, not other browsers. Do not remove archive preservation from the existing in-place migrator until this replacement path is implemented and verified.
  • For same-schema whole-database retention, prefer Turso's native database-copy/create-from-recovery-point operation over a custom row copier, subject to a real restore check. A finite recovery window is not long-term retention; keep independently named copies for the required archive lifetime. Use logical op-log conversion only for schema or scope changes. Read-only archives and restricted credentials prevent ordinary sync clients from mutating retained copies.
  • Restore to a fresh database URL and a clean isolated local profile/database by default. Stop sync first and export unsent edits. A cursor reset alone is not point-in-time recovery: acknowledged outbox entries are deleted, stale local-only rows can survive replay, and bootstrap can upload them again (syncEngine.ts:537-543,559-586). Keep that export separate; applying it later is an explicit merge, not restoration of the snapshot.
  • Do not support in-place snapshot restore through the ordinary sync loop. If added later, it requires a new history generation visible to every client, stopping old writers, rebuilding local state, and deliberately resetting target cursor/watermark/bootstrap state. A lower remote rev can warn about rewind but cannot detect every divergent history. Preserve unknown/newer-target refusal; do not weaken it to a name-prefix check.

3.4 Scope reduction — sync only user data

Finding. User-only sync needs a store-specific ownership policy plus dependency retention, not one row predicate. Seed notes are marked, but applySeedChunk also writes unmarked immutable revisions, tags, pages and links, static projections, and bundled definitions (runtime.ts:257-380). Payload reduction has not been measured. Preserve current full-data sync until the policy below can restore user state without missing references.

  • Classify each store using its actual provenance: note seedOrigin, projection isStatic plus owner note, definition registrySource, and link ownership. Never infer user authorship from userId or the absence of seedOrigin. Keep uncertain rows until their derivation and reconstruction are proven.
  • meta mixes seed checkpoints with preferences and other state. Exclude import checkpoints/claims under seed:, not the whole store; keep existing non-seed meta behavior unless explicitly changed. Source registration, subscriptions, and auto-sync choices also live in separate localStorage keys (docs/adrs/0002-catalog-source-lifecycle.md:38-98). They are not backed up by filtering IndexedDB; exclude credentials and define a separate safe settings export if restoration needs those choices.
  • field_catalog, field_sources, field_values, and field_catalog_meta are not seed-only. Field contributions come from user note frontmatter and workout event metrics (services/catalog/fieldCatalog.ts:136-194). Keep them initially. Exclude derived field data only after a deterministic rebuild from all retained user sources is implemented and verified before field queries run.

Required changes.

  • Retain user notes, sessions, events, attachments, custom definitions, links and their required immutable revisions. Sessions pin [noteId, blockId, blockVersion]; current seed chunks may not reproduce an old revision (packages/storage/src/validation.ts:88-104). Keep revision history conservatively until dependency closure is proven. Before excluding a seed parent, preserve the content/identity needed by retained user references. Re-import latest seed is not a substitute for saved workout history.
  • At journal time classify both previous and new ownership inside the write transaction. User→user and seed→user emit complete user puts with dependencies; user→seed emits a tombstone for the former user record, not a silent dropped put. Deletes inspect pre-delete ownership, including expanded key ranges. Ordinary deleteNote has no durable seed-deletion suppression (StorageService.ts:264-303); import claims are concurrency locks, not deletion intent. Preserve current delete behavior until durable user tombstones and seed-import suppression are implemented together.
  • Do not rewrite wipe into raw clear operations on mixed stores: replay still clears seed rows, and clear(block_revisions) is deliberately ignored on pull. Define user-scope clear/wipe as explicit eligible-key tombstones with dependency-aware history rules, or as a new versioned protocol operation. Keep explicit all-data wipe distinct. Local deletion and its journal must commit atomically; no filter rollout until both writer and reader semantics agree.
  • One shared ownership policy must govern outbox creation (IndexedDBStorage.ts:107-171,299-337), atomic bootstrap snapshots (syncEngine.ts:461-503), and migration snapshots (syncEngine.ts:351-410). The policy may need prior rows and referenced records; it cannot be just include(row). Preserve ordering and include referenced history before consumers need it.
  • Use a fresh target and an explicit compatibility transition when filtered semantics ship. Old outbox groups and old remote logs still carry full-data clears/wipes; old clients can keep writing them. Build a policy-compliant snapshot and convert pending writes, then retire old writers. Do not claim that upload-only filtering makes mixed-version replay harmless.
  • Acceptance at the existing sync.check.ts seam must prove fresh-profile restoration with edited seed notes, user references to old seed revisions, bundled versus custom definitions, user field discovery, seed-note deletion/re-import, ownership transitions, key-range deletes, clear/wipe, failed-upload retry, and obsolete-client refusal. These are required implementation checks, not tests already added by this document revision.

3.5 DB-to-DB migration

Finding. Three reuse claims, three different answers:

  • applySyncBatch can copy same-schema groups in source revision order into a fresh, exclusively reserved target. Preserve group identity and payload for retries of that exact copy. It assigns target-local revisions; it does not perform conflict-aware multi-database merge. A distinct conversion needs distinct stable operation identities.
  • publishCatalogSeed is not a backup round-trip, even after materializing domain tables. It exports only catalog notes and block projections, omitting sessions, events, attachments, general metadata, and full revision history (publish.ts:35-77,112-160). Import derives note IDs from paths, sets seed ownership, and can assign new versions (runtime.ts:259-305). A browser-only backup has no domain notes for it to read. Keep seed publication as an optional one-way catalog export, not a migration dependency.
  • Extract the existing scratch conversion only when implementing cross-version copy. It relies on idb and the browser upgrade chain; fake-indexeddb in sync.check.ts proves a test adapter, not production CLI parity. A CLI runtime needs an explicit shipped adapter, per-run scratch identity and cleanup, plus binary and legacy-version restoration checks. Do not rewrite the migration chain in SQL merely to avoid selecting that adapter.

Required changes.

  • Migration procedure: freeze all source writers, record schema and terminal revision, reserve a fresh target exclusively, then read one consistent source snapshot. Reject or restart if the source changed. Validate every operation and conversion; missing stores/keys, unknown operations, or missing pinned revisions must fail the copy, never silently drop rows. Verify full restoration and binary payloads before publishing the target URL. Keep incomplete targets out of browser settings and retain the source on every failure.
  • Bootstrap retry identity must refer to one immutable snapshot, not just a browser. Persist a run ID and frozen snapshot/chunk manifest for retries, or abandon that run and start a new one against a fresh target. Random IDs per retry also break idempotency by appending obsolete chunks again. Different browser UUIDs already avoid normal cross-browser collisions; same-browser rebootstrap against copied/retained IDs is the actual risk.
  • replaceSyncLog remains an in-place conversion primitive, not the default for versioned retention. Atomic replacement alone does not protect its earlier read/convert phase: the current function checks initialization but not expected source schema/revision (sync.ts:380-409). Any retained in-place path needs source schema/revision compare-and-swap and replay-generation handling across clients. Fresh-target copy avoids mutating the retained archive.

3.6 Where the version lives

Finding. Today the version that matters — the sync payload schema — lives in the remote database's _wodwiki_sync_state row (written by initSyncTarget, enforced by expectSchema inside the write transaction, sync.ts:215, sync.ts:287-293). The proposal adds version to localStorage (playground) and .env (CLI) as a second, writable source of truth.

Required changes.

  • The remote state row is canonical for payload schema. localStorage and .env select a complete target URL; do not add a second editable schema value. A name is descriptive, not proof of schema or database identity. A restored history must not inherit another history's cursors merely because schema and URL match.
  • Settings writes trigger sibling-tab reload (dataSettings.ts:191-201). Do not auto-rewrite a live target on app update. Switch only after the new target passes copy/restore validation and unsent edits have an explicit disposition. Other devices still require writer retirement or deliberate re-pairing.
  • Reuse existing DB_VERSION compatibility checks and CLI resolution. Do not add a parallel name-to-URL resolver or hardcoded seed epoch. Provisioning supplies the actual URL; preserve flags > process env > .env and reject conflicting selectors (config.ts:311-374).

4. Pitfalls of the existing design (catalog)

  1. P1. Dual-channel divergence. Browser op logs and CLI/server domain tables have no ongoing reconciliation. Keep live targets separate. An isolated one-way materializer can support catalog export, but does not make publishCatalogSeed a lossless backup or shared-writer protocol (§3.2, §3.5).
  2. P2. Restore can resurrect newer local state. URL-hashed cursors survive a same-URL restore; resetting them neither erases stale local rows nor restores already acknowledged outbox history. Pending overlays and automatic bootstrap can reintroduce post-snapshot edits. Use a fresh remote identity and isolated clean local restore with uploads held until validation; handle unsent edits separately (§3.3).
  3. P3. Bootstrap IDs can identify different payloads. Different browser UUIDs normally prevent collisions. The risk is restarting seq for a changed snapshot with the same persisted browser UUID while the target retains or copies the earlier IDs. Idempotent insert silently skips those changed groups. Bind retry IDs to immutable snapshot content (§3.5).
  4. P4. Archive growth and missing generation metadata. Each replacement archives the active log with no retention policy; old schema markers are not versioned alongside archived ops (sync.ts:380-407). Preserve current archives until an independently verified whole-database retention path replaces them. Record schema, source identity, snapshot time, and restore procedure with retained backups.
  5. P5. Destructive replay crosses ownership. Current wipe clears every non-system store and ordinary clear clears mixed-origin stores (IndexedDBStorage.ts:448-460). Raw per-store clears do not fix this, and revision clear is ignored outside explicit wipe. Seed re-import cannot be assumed to reconstruct historical user pins. Define new scope semantics before enabling filtering (§3.4).
  6. P6. Migration floor at v20. Older schemas are refused (syncEngine.ts:351-356). Retention does not imply current restore support. Keep archives intact and publish only tested conversion paths.
  7. P7. Read/convert/write is not an atomic migration. Conversion reads the full history outside the replacement transaction. Another device can append before replacement and be omitted from the converted snapshot; the local Web Lock cannot prevent it. Freeze writers or enforce source schema/revision compare-and-swap. Full-history replay also has unmeasured client memory/time cost (syncEngine.ts:351-410).
  8. P8. Classification is not identity verification. A recognized state table takes precedence, and otherwise _wodwiki_* names are ignored in the foreign-table check (sync.ts:188-210). Keep refusals, but do not claim the probe proves ownership or completeness. Provision into an exclusively reserved target and verify required tables/state; a prefix alone is never authorization.
  9. P9. Attachment sizing is not a hard 1 MB ceiling. Upload batching estimates binary size but admits an oversized first atomic group; bootstrap estimates JSON.stringify(row).length, which can undercount binary data (syncEngine.ts:120-131,495-499,527-535). Preserve groups and binary fidelity. Validate encoded payload limits against the selected transport; do not promise that large attachments are already chunked.
  10. P10. Membership is not authorship or authorization. The current default membership is local identity, not remote access isolation. Seed-derived rows without origin flags can receive user stamps. Do not use USER_OWNED_STORES or userId as a complete seed filter; multi-user remote sharing requires a separate authorization design.
  11. P11. Concurrent first-contact bootstrap can skip another device's rows. The empty-target path uploads its snapshot, then saves the target's post-bootstrap revision as its pull cursor (syncEngine.ts:309-317). Another device can append during that interval; those unseen groups fall behind the saved cursor. This source-audited race is separate from UUID reuse and was not reproduced in this document-only revision. Required fix: replay from the pre-bootstrap boundary, or zero for a newly initialized target, rather than skipping every group through the later probe. Add a deterministic two-device interleaving scenario at the existing sync-check seam.

5. Decisions and remaining questions

#QuestionWhy it matters
Q1 What is a user-deleted seed note under user-only sync? Current deletes are journaled. A proposed filter must preserve user deletion intent through durable tombstones and import suppression before dropping seed deletes (§3.4).
Q2 Which settings must a fresh-profile restore recover? Keep non-seed IndexedDB meta initially. Source subscriptions and auto-sync choices in localStorage need a separate safe export; tokens must stay out of it (§3.4).
Q3 Default decided: fresh remote identity and isolated clean local restore. Cursor resets alone are unsafe. In-place recovery is excluded until all clients can detect a new history generation and retire old state (§3.3).
Q4 Default decided: separate live browser-backup and CLI/server targets. No continuous op-log/domain-table reconciliation exists. Optional one-way catalog export does not permit shared live writers (§3.2).
Q5 Default decided: live names describe storage compatibility, currently DB_VERSION. Do not fork for app or seed releases alone. Archive/restore identities remain distinct from schema versions (§3.1).
Q6 Which documented recovery operations and limits apply to the deployed account? The live spec distinguishes v1 create-from-database/recovery-point from v3 deleted-database recovery. Verify plan eligibility, credential retirement, and an actual restore; CORS does not change the security boundary (§3.2).
Q7 Retention: how many versioned DBs, and who deletes old ones? Set a retention owner, quota budget, and tested restore window. Never auto-delete the last verified recovery copy; destructive commands need explicit target confirmation.
