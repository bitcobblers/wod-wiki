Architecture & UI System Audit

Workout Results Presentation: Cross-Screen Inventory & Standardization

Target: apps/playground · Analysis of Results Display Modalities, Root Causes of Divergence, and Proposed Unified Component Hierarchy

1. Executive Summary

Throughout the playground application, recorded workout results (sessions, segments, and events) are surfaced across at least eight distinct user journeys. Today, each surface independently solves the problem of how, when, and where to render results. The consequence is inconsistent visual vocabulary, diverging interaction affordances, fragmented data granularity, and cognitive friction for the user.

This document details the exact mechanics of how each screen presents results, the engineering reasons behind why they diverged, and a concrete architectural proposal to standardize result displays across the application based on clear screen typologies.

2. Current State Inventory: Where, When, Why, and How

Workout executions generate a Session record, an array of EventRecords, and associated BlockRevision pins in IndexedDB. Below are the eight distinct surfaces that consume and present this data.

1. Playground Scratchpad Detail (PlaygroundNotePage) Ad-Hoc Unstyled List

Route: /playground/:id

Where: Rendered in a raw <section aria-label="Workout results"> pinned at the very bottom of the document editor page (below the CodeMirror editor and BlockHistory component).

When: Whenever a note has recorded sessions in IndexedDB, fetched via storageService.getSessionsForNote(runtimeNoteId).

Why: Added as a quick way for users running workouts in a scratchpad note to verify that their run saved and navigate to the resulting detail.

How: Formats duration via formatDurationSmart(result.duration) and date via formatDateShort. Displays an unstyled bulleted list with an optional text chip saying "partial" if uncompleted. Clicking navigates to /results/:sessionId.

Weaknesses: Does not indicate which block inside the document generated the result if the note has multiple workouts. Uses plain text links without icons, paces, reps, or scores. Inconsistent with every other results component in the app.

2. Canonical Vault Note (NoteByIdPage) Sidebar Badges Only

Route: /notes/:noteId or /p/:slug

Where: Results are NOT displayed in the body of the note at all. They only appear as numeric badges in the L3 table of contents rail via useNotePageNav.

When: The page loads note sessions via storageService.getSessionsForNote(noteKey) and listens to onResultSaved.

Why: Vault notes are treated as authoritative documents; designers avoided cluttering authored prose with execution artifacts.

How: Passes results to useNotePageNav, which invokes groupResultsByVersion and decorates TOC links with resultCount and hasResult.

Weaknesses: A user visiting a note they worked out against cannot see their time, score, or history without opening the editor gutter companion or navigating away to /sessions.

3. Journal Day View (JournalDatePage) Inline CodeMirror Inlays + L3 TOC

Route: /journal/:date

Where: Directly below the workout fence inside the CodeMirror editor buffer, plus outline badges in the navigation rail.

When: When opening a journal entry for a date that has recorded workout sessions.

Why: The Journal is an athlete's logbook. The workout prescribed on that date should visually show the logged execution immediately beneath the prescription.

How: Uses resultListItemDOM.ts (an imperative DOM builder mirroring ResultListItem.tsx) inside a CodeMirror WidgetType extension. Displays timestamp (e.g. "10:30 AM"), workout title, duration, and completion status checkmark.

Weaknesses: Custom widget injection logic coupled to CodeMirror DOM lifecycle; not reusable outside of the editor buffer.

4. CodeMirror Active Companion (WhiteboardCompanion) Contextual 35% Sidebar Drawer

Route: Any editor surface when cursor is inside a wod block.

Where: The right-hand editor companion drawer (35% width rail).

When: Focused inside an executable block (time, amrap, emom, etc.).

Why: Provides micro-level contextual intelligence while authoring or reviewing a specific block without leaving the editor.

How: Calls useScriptBlockResults(noteId, sectionId, extendedResults, section?.contentId) and useScriptLineResults. Displays a history counter badge, the latest result summary line, and historical runs sorted descending.

Weaknesses: Only visible when the companion is expanded and the cursor is actively inside the block bounds. Invisible on mobile or when reading in view mode.

5. Post-Workout Execution Debrief (FullscreenTimer / ResultsView) Full-Bleed Analytics Matrix

Route: Modal overlay in /run/:runtimeId or MarkdownCanvasPage upon timer stop/completion.

Where: Fullscreen modal stage.

When: Immediately upon athlete completion or explicit timer stop.

Why: The athlete needs an immediate, rich breakdown of their performance: total time, segment splits, round paces, workload, and heart rate metrics.

How: Mounts ReviewGrid alongside AnalyticsScorecard. Pivots IOutputStatement metrics into tabular columns, flags PRs, and highlights round deviations.

Weaknesses: Transient; once dismissed, this specific layout cannot be re-opened directly from the note without navigating through /results/:sessionId.

6. Canonical Session Detail (/results/:sessionId) WQL Stream Segment Table / Cards

Route: /results/:sessionId

Where: Dedicated route hosting QueriableStreamView.

When: Navigated to from a result link (e.g. from PlaygroundNotePage, WallClock completion, or /sessions).

Why: Serves as the permanent, linkable deep-link for a single recorded execution.

How: Configured via createResultDetailProfile(resultId) with default WQL query :session{result:<id>, plane:segment}. Renders via PropertyTable (tabular segment rows) or StreamFeed (segment cards).

Weaknesses: Displays raw segment rows rather than a unified workout summary card. Feels like an analytics query tool rather than an athlete's scorecard.

7. Sessions Audit Stream (/sessions & /session/:date) Stream Feed Cards & Property Table

Route: /sessions

Where: Primary navigation stream surface.

When: Browsing recent activity or filtering by workout/date in the main navigation.

Why: Chronological overview of all workout sessions executed across the app.

How: Powered by SESSIONS_STREAM_PROFILE with query :session{} last 1d. Renders items as LibraryRow cards with trophy icons, duration pills, timestamp headers, and "Compare" actions.

Weaknesses: High-level card format optimized for lists; does not embed segment splits or round breakdowns.

8. Television / 10-Foot Display (review-panel-chromecast.tsx) High-Contrast Remote Display

Route: Chromecast receiver tab / cast receiver window.

When: When casting a workout to a TV.

Why: Standard desktop grids are illegible from 10 feet away.

How: Consumes reviewData.rows and analyticsSummary.projections into large-font summary cards navigable via D-pad.

Weaknesses: Specialized receiver-only surface; completely decoupled from web UI components.

4. Core Architectural Gaps & Failure Modes

  • Block-to-Session Disconnection: Notes can contain multiple workout blocks (e.g. warmup, strength, metcon). PlaygroundNotePage groups all sessions at the bottom under the whole Note ID without attributing which block was run.
  • Presentation Discontinuity: Running a workout in /playground/:id gives the athlete a high-fidelity ReviewGrid inside FullscreenTimer. But once closed, the note only shows an unstyled bullet list: 04:12 Oct 12. The visual payoff is immediately lost.
  • Missing Shared Component: ResultListItem.tsx was built to be the canonical result card, but only JournalDatePage and CodeMirror inlays use it. PlaygroundNotePage re-invented a plain list, and LibraryRow implemented its own separate result presentation.
  • Lack of an Expandable Session Ledger: Vault notes and playground notes lack a standardized "Results Ledger" drawer or accordion that can expand to show the scorecard and splits without navigating to a separate route.

5. The Standardization Strategy: A 5-Tier Results Hierarchy

Rather than treating results presentation as screen-specific ad-hoc UI, the playground should adopt a unified, composable 5-tier presentation hierarchy:

Tier 1: Micro Badge (Navigation & TOC)

Role: Presence indicator.

Component: ResultBadge (extracted from useNotePageNav).

Display: Pill showing execution count and latest badge (e.g. 2 runs · 04:12 PR). Appears in table-of-contents rails and companion headers.

Tier 2: Inline Summary Row (Document Flow)

Role: Compact record beneath the block.

Component: Standardized ResultListItem (React component & CodeMirror widget share exact same view-model).

Display: Timestamp, completion icon, total duration, score/load, and chevron to expand detail.

Placement: Directly underneath completed blocks in Journal, Playground, and Vault notes.

Tier 3: Document Results Ledger (Note Bottom / Drawer)

Role: Comprehensive session history for the entire document.

Component: <NoteSessionLedger noteId={...} />.

Display: Grouped by workout block. Each section header identifies the workout name, followed by chronological ResultListItem cards with quick-expand triggers for segment splits.

Placement: Replaces the raw <section> in PlaygroundNotePage and added to NoteByIdPage.

Tier 4: Scorecard & Segment Matrix (Detailed Debrief)

Role: Full execution debrief.

Component: ResultsView (composed of AnalyticsScorecard + ReviewGrid).

Display: Segment splits, round paces, stroke rates, heart rate zones, and personal record trophies.

Placement: Used in FullscreenTimer post-workout modal AND accessible via drawer/dialog from any ResultListItem.

Tier 5: Telemetry Stream & Exploration

Role: Cross-session querying and granular data analysis.

Component: QueriableStreamView (with PropertyTable or StreamFeed).

Placement: /results/:sessionId, /sessions, and /analytics/explorer.

7. Implementation Steps & Action Items

  1. Extract <NoteSessionLedger>: Replace the bespoke raw <section aria-label="Workout results"> in PlaygroundNotePage.tsx with a reusable component that groups sessions by block and renders standardized ResultListItem cards.
  2. Unify ResultListItem View-Models: Align ResultListItemViewModel between the React component and resultListItemDOM.ts, adding block name attribution and quick metric pills (e.g. total reps, average pace).
  3. Add Direct Modal Inspection: Allow clicking any ResultListItem anywhere in the app to open the full ResultsView (Scorecard + ReviewGrid) in an inline dialog without forcing a full-page navigation to /results/:sessionId.
  4. Adopt Ledger in NoteByIdPage: Expose the <NoteSessionLedger> behind a collapsible "History & Results" disclosure in canonical vault notes.
