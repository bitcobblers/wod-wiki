Catalog Architecture Explainer

How distributed workout catalogs are authored, published, subscribed, imported, updated, and removed — end to end, with the exact storage keys and invariants.

ADR-0001ADR-0002 Canonical model definitions: docs/adrs/0001-catalog-seed-data-contract.md and docs/adrs/0002-catalog-source-lifecycle.md.

1. The System at a Glance

The catalog system has two sides that only ever touch through two static files: a manifest and a set of immutable chunks. There is no API, no server, no dynamic anything — a catalog is a directory of JSON served by any static host (GitHub Pages is the reference flow).

The one rule that makes everything else cheap: the manifest alone tells a consumer whether anything changed. A version number (git commit count) and per-chunk sha256 hashes mean the common case — nothing new — costs one small HTTP fetch and zero writes.

2. Publisher Side: Markdown to Published Seed

2.1 Scaffolding a catalog repository

wod init-catalog <name> (packages/tools/src/cli/scaffoldCatalog.ts) generates a publish-ready repository: a markdown/collections/<name>/ corpus with README + one workout per file, a package.json (whose name, description, and repository fields become manifest metadata), and a GitHub Actions workflow that runs bunx wod build . --output dist and publishes dist/ to Pages. The destination directory must not already exist — the command refuses to overwrite.

2.2 The wod build pipeline

StageWhat it does
Scan + partitionEvery markdown/**/*.md file is assigned a chunk by chunkIdFor(relPath): collections/<dir> → collection.<slug>, feeds/<dir> → feed.<slug>, plus reserved chunks canvas, dashboards, efforts, template. An unrecognized path is a hard parity failure, never a silent drop.
GatesDashboard gate (≥3 widgets, known widget types, WQL must parse, $token declared) then the WOD syntax gate (Lezer error-node scan of plain fences, parseScript on dialect fences). Any failure aborts the build.
Compile passesbuildBlockIndexRows projects every fenced block into a BlockIndexRow (exactly one projection per block); buildBlockEffortRows links wod blocks to canonical effort slugs. Rows are grouped back per file into SeedRow { path, content, blocks, blockIndex, blockEfforts }.
WritePer chunk: rows serialized to chunks/<id>.<sha256-8>.json; the manifest records the full sha256, byte size, and row count. An HTML build report is written alongside.

  "version": 2841,
  "versionLabel": "v0.36.2135-1-gea2c9808a-dirty",
  "commit": "ea2c9808…",
  "dirty": true,
  "builtAt": "2026-10-16T18:10:02.356Z",
  "chunks": [
    { "id": "collection.crossfit-girls", "path": "chunks/collection.crossfit-girls.b8f29e2a.json",
      "sha256": "…64 hex…", "bytes": 7531, "count": 21 }

}

version is the git commit count, not a timestamp — it is monotonic, human-meaningful ("you have 2841, published has 2850"), and doubles as Note.createdAt at import so identical content never produces spurious diffs. schema is pinned to SEED_SCHEMA = 8 in both copies of contract.ts; a consumer receiving any other value refuses with "rebuild seed artifacts".

3. Import: Chunk Rows into IndexedDB

Both import drivers (CLI importSeedDir and the app's runSourceSync) converge on one engine primitive: applySeedChunk(storage, write) (packages/engine/src/seed/runtime.ts), a single readwrite transaction over notes, block_revisions, block_index, block_efforts, page, page_notes, tags, note_tags, efforts, meta.

3.1 Invariants enforced inside the transaction

  • Deterministic identity. seedNoteId(path) (SHA-1 of a fixed namespace UUID + path, formatted as a v5 UUID) maps a row path to a note id. Re-importing unchanged content is idempotent; two sources cannot collide.
  • User data wins. A note is imported only if absent or stamped seedOrigin === 'seed' and owned by this chunk. User-owned notes are counted as skippedUserOwned and their static projections are never deleted.
  • Checkpoint compare-and-swap. expectedMeta must deep-equal the stored seed:<id> row in-transaction; a mismatch aborts with "Seed checkpoint changed during import". This is also the multi-tab claim mechanism (see 4.4).
  • Tombstones. Notes recorded in the checkpoint but not re-declared by the new chunk (or absent from the manifest entirely) are deleted with their tag/page links — only when still seed-owned.
  • Structural re-validation. assertSeedRows re-parses every block and recomputes every blockContentId fingerprint at import. A hand-edited chunk file is rejected, not silently corrupted.
  • No rollback. A manifest whose version is below the checkpoint's seedVersion is refused before any write.

4. Consumer Side: Sources, Subscriptions, and the Boot Flow

4.1 Three independent documents

DocumentStorage keyMeaning
Source registrywodwiki.seedSources (+ .hidden)Custom sources the user added: { id, label, url, repositoryUrl? }. URLs are normalized (absolute https, no credentials/query/hash, trailing slash); duplicates rejected against both the registry and built-in URLs. Built-ins hidden by Delete land in .hidden; core is never hideable.
Subscription mapwodwiki.seedSubscriptions{ [sourceId]: boolean }. Absence = no explicit choice. Core is hardcoded always-subscribed. Subscribing never implies auto-updating.
Auto-sync mapwodwiki.seedAutoSync{ [sourceId]: boolean }, default core on / all others off. Drives check-only vs apply in the background pass.

Defaults from defaultSeedSources(), in resolution order: core (build-embedded ${BASE_URL}seed/core/, autoImport true, version stamped from __SEED_VERSIONS__) → community (https://bitcobblers.github.io/wod-wiki-community/, opt-in) → five per-catalog FeedSeedSource slices of the community manifest (CrossFit programming, Dan John 40-day, Girls, Heroes, dashboards) → custom sources (embeddedVersion 0, never boot-imported).

Side documents: wodwiki.seedChecks (last successful manifest check per source, best-effort) and wodwiki.seedImport.enabled (feature flag; '0' opts out).

4.2 Boot: first visit vs returning visit

First visit (no core checkpoint)Returning visit (checkpoint exists)
GatemarkSeedSyncStarted() → readiness 'preparing'; stream shows a skeletonmarkSeedSyncSettled('current') immediately — works fully offline
What runsrunBootSeedSync filtered to autoImport !== false (core only). The gate flips 'ready' the instant the canvas chunk commits (onFirstPaint) while remaining chunks still import.One background run over core + subscribed sources with probeManifests: true; outcomes never touch the gate.
ThenIf any non-core source is subscribed, a second nonblocking background run checks them.Grouped update notification fires if anything is pending.

Readiness states: idle | preparing | ready | error (idle reads as ready), mirrored onto <html data-seed-state> / data-seed-outcome for e2e. Multi-tab convergence rides a BroadcastChannel('wodwiki.seed') with seed-imported and seed-removed messages.

4.3 Background check: check vs apply

Every subscribed source's remote manifest is fetched and version-compared on page load (the skip-fetch fast path requires schema === 8 && seedVersion === embeddedVersion > 0; background checks bypass it with probeManifests). Then:

  • Auto-sync ON → chunks with changed sha256 are fetched and applied; the checkpoint advances.
  • Auto-sync OFF → check-only: no chunk fetch, no checkpoint write. The detected update lands in the run's CatalogUpdatesSnapshot as 'pending'.

Background mode publishes exactly one snapshot per run; the UI toasts it once with a "Review updates" action that deep-links to /catalogs?manage=1. Manual sync of a source clears its entry; an empty list clears the notification. Per-source manual activity uses a separate syncActivity channel, suppressed during background runs. Outcomes aggregate worst-first: disabled < current < busy < imported < server-stale < error < update-pending, with update-pending treated as ready by the gate's preparing branch.

4.4 The multi-tab claim

An import stamps claim { owner, at } on the checkpoint row before fetching chunks. A fresh claim owned by another tab yields outcome 'busy' (the readiness gate retries after the TTL and converges via the seed-imported broadcast). A claim older than SEED_CLAIM_TTL_MS = 45 000 ms is assumed abandoned (crashed tab) and is stolen. The finally block releases the claim only if still the owner.

4.5 /subscribe?source=… intake and consent

  1. No ?source → redirect to /catalogs.
  2. Page-level URL validation mirrors normalizeSeedSourceUrl (https only, no credentials/query/hash, trailing slash).
  3. The manifest is fetched and validated before anything is shown; a failure renders an error and writes nothing.
  4. The consent screen discloses name, URL, description, published version, builtAt, schema, chunk/item counts, download size, and repository link — plus an explicit "opening this link has not added any content or source" notice — with an auto-sync checkbox.
  5. Import Once / Import & Subscribe: match an existing source by normalized URL or addCustomSeedSource, then syncSeedSource(id, { subscribe: false }); Subscribe additionally persists auto-sync + subscription (with an explicit storage-unavailable error if persistence fails). Success navigates to /catalogs?manage=1. Decline & Dismiss writes nothing.

Import-once records an explicit false for a new source so the boot migration (migrateSeedSubscriptions, which adopts previously imported but unchosen sources with seedVersion > 0) cannot silently subscribe it later.

4.6 The manager drawer (?manage=1)

A thin Dialog wrapping the same SyncSection used by /settings/sync, opened from the grouped update toast, the subscribe success screen, or the in-page toolbar button. Closing deletes only the manage query param (other params like q survive) and uses history.replace so a modal never stacks history. Each row shows identity + version info, a Sync button when an update is pending, Subscribe when unsubscribed, an auto-sync checkbox, and a "…" menu with the published-HTML link, git source link, Unsubscribe, and Delete.

4.7 Unsubscribe vs Delete, and what removal touches

ActionDoesKeeps
UnsubscribeDeletes imported content + checkpoint; subscription → false; auto-sync → false; clears pending-update entry; broadcasts seed-removed. Core: no-op.The source registry row — Subscribe works again later.
DeleteUnsubscribe plus registry removal: removeCustomSeedSource for custom sources, hideSeedSourceRow for built-ins.Nothing of the source; user data untouched.

Deletion is one readwrite transaction over notes, attachments, note_tags, block_index, block_efforts, page_notes, meta keyed by the checkpoint's recorded noteIds, and only for notes still stamped seedOrigin === 'seed'. Never touched: user-authored notes, tags, page, block_revisions, sessions, events, sync stores, other sources' checkpoints, and the wodwiki-telemetry / wodwiki-user-calcs databases. Storage failure propagates — a deletion error is never swallowed, so a stale checkpoint can never trigger a zombie re-import.
