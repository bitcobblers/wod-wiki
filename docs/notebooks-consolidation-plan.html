Architecture Consolidation Proposal
Everything Is a Note; Every Container Is a Notebook
Consolidating Journal, Playground, Guides, Collections, Feeds, and Catalogs into a single Note + Notebook (notebook/{slug}) model with predefined defaults (notebook/journal, notebook/playground, notebook/guides), user-created notebooks, and seed-delivered notebooks linked to their source URL.
Grounded in: packages/core/src/types/storage.ts · packages/engine/src/seed/contract.ts · packages/wql/src/QueryService.ts · apps/playground/app/lib/entryMapper.ts · apps/playground/src/services/NotebookService.ts · apps/playground/app/nav/appNavTree.ts

1. Executive Summary & Core Invariants

Today the codebase models the exact same domain relationship—a markdown workout note living inside a named container—four different ways depending on where it came from: Journal entries, Playground scratchpads, Seed Collections/Feeds, and localStorage Notebooks. This plan collapses those parallel abstractions into two orthogonal primitives:

Primitive 1: Note (The Content)

Every workout, dated training log, scratchpad script, and benchmark workout is a Note. Journal entries, Playground pages, and Collection/Feed items stop being separate NoteKind / EntryKind types and become ordinary Note rows scoped to a notebookId.

Primitive 2: Notebook (The Container)

Catalogs, Collections, Feeds, Guides, Journal, and Playground all become Notebooks with canonical notebook/{slug} identifiers (including notebook/journal, notebook/playground, and notebook/guides). Users can create additional notebooks on /notebooks, and seed sources deliver notebooks tied to the source URL entry.

Four Governing Rules of the Consolidated Model:

  1. Predefined Default Notebooks (notebook/{slug}): Every notebook uses a canonical notebook/{slug} identifier. notebook/journal, notebook/playground, and notebook/guides are the built-in default notebooks.
  2. User-Created Notebooks: On the /notebooks page (replacing /catalogs), users can create, rename, describe, and delete additional custom notebooks (e.g., notebook/2027-open-prep).
  3. Application-Level Editability & Source URL Linkage: Read-only status is never a separate stored flag—the application layer decides editability based on origin/type: only user-created notes (seedOrigin !== 'seed') are editable. Seed-delivered notebooks (e.g., notebook/crossfit-girls, notebook/guides) are tied to the seed source entry and URL where the content was pulled from, and allow cloning workouts into user-writable notebooks.
  4. Precedence Preservation: When multiple seed sources deliver the same notebook/{slug} or note path, the established precedence hierarchy (core < community < imported < user) resolves collisions deterministically.

3. Target Architecture: Before vs. After

3.1 Unified Domain Models

export type DefaultNotebookSlug = 'journal' | 'playground' | 'guides';
export type NotebookId = `notebook/${string}`;

export interface Notebook {
  /** Canonical notebook identifier — always 'notebook/{slug}', including 'notebook/journal', 'notebook/playground', 'notebook/guides' */
  id: NotebookId;
  /** Bare slug segment ('journal' | 'playground' | 'guides' | user slug | seed slug) */
  slug: string;
  title: string;
  description?: string;
  icon?: string;
  /**
   * Provenance tier:
   * - 'default': predefined 'notebook/journal', 'notebook/playground', 'notebook/guides'
   * - 'user':    created by the user on /notebooks
   * - 'seed':    delivered by a seed manifest chunk
   *
   * Note: read-only is NOT stored on Notebook; the application layer derives
   * editability from origin/type (only user-created notes are editable).
   */
  origin: 'default' | 'user' | 'seed';
  /** Registered seed source entry id ('core' | 'community' | CustomSeedSource.id) */
  sourceEntryId?: string;
  /** Canonical seed directory URL where the source is pulled from (SeedSourceSpec.url / CustomSeedSource.url) */
  sourceUrl?: string;
  /** Optional published repository URL from the seed source entry */
  repositoryUrl?: string;
  /** Seed chunk id (e.g. 'collection.crossfit-girls' or 'feed.dan-john-40-day') when delivered by a seed */
  seedChunkId?: string;
  /** Optional README / landing markdown note id for rich notebook headers */
  landingNoteId?: string;
  createdAt: number;
  updatedAt: number;
}

export interface Note {
  id: string;
  /** Canonical notebook id ('notebook/journal', 'notebook/playground', 'notebook/guides', 'notebook/crossfit-girls', etc.) */
  notebookId: NotebookId;
  title: string;
  rawContent: string;
  sourceRevision: number;
  blocks: Record<string, NoteBlock>;
  /** Optional calendar date (noon UTC ms) — used by journal and dated programs */
  date?: number;
  createdAt: number;
  /** System note discriminator only when non-standard: 'note' | 'dashboard' | 'effort' | 'equipment' | 'guide' */
  type?: 'note' | 'dashboard' | 'effort' | 'equipment' | 'guide';
  /** Explicit clone lineage: the source Note.id this note was cloned from */
  clonedFromNoteId?: string;
  /** Ownership marker: application layer allows editing ONLY when seedOrigin !== 'seed' (user-created) */
  seedOrigin?: 'seed' | 'user';
  seedVersion?: number;
  seedChunkId?: string;
  sourcePath?: string;
}

/** Application-level editability policy: only user-created notes are editable. */
export function isNoteEditable(note: Pick<Note, 'seedOrigin'>): boolean {
  return note.seedOrigin !== 'seed';
}

3.2 Seed Delivery & Source URL Linkage

  • One Seed $\to$ Many Notebooks (Linked to Source URL): Each seed chunk (canvas $\to$ notebook/guides, collection.<slug> / feed.<slug> $\to$ notebook/<slug>) resolves its Notebook record with sourceEntryId and sourceUrl bound directly to the registered SeedSourceSpec / CustomSeedSource entry where the seed is pulled from.
  • README Landing Note: A notebook's README.md (if present in the chunk) is linked via Notebook.landingNoteId, rendering the notebook's overview prose above its note stream.
  • Application-Decided Editability & Clone-on-Write: Because only user-created notes (seedOrigin !== 'seed') are editable, seed notes in notebook/guides or notebook/crossfit-girls render read-only in the editor and provide a Clone to Notebook action targeting notebook/journal, notebook/playground, or any user-created notebook/<slug>.

5. UI & Navigation Consolidation Plan

5.1 Navigation Tree (`apps/playground/app/nav/appNavTree.ts`)

Today the L1 sidebar has four separate note-container items: Journal, Catalogs, Feeds, and Playgrounds. Under the consolidated model:

  • Journal (/journal, alias for /notebooks/journal) and Playground (/playground, alias for /notebooks/playground) remain quick-access predefined defaults in L1 (or pinned at the top of the Notebooks L2 panel).
  • Catalogs (/catalogs) and Feeds (/feeds) merge into a single Notebooks (/notebooks) L1 zone (with `/catalogs`, `/feeds`, `/c/:slug`, and `/collections/:slug` redirecting or aliasing cleanly).
  • The Notebooks L2 Panel lists:
    1. Primary action: + New Notebook (opens the Create Notebook dialog) and + New Note (creates a note in the active writable notebook).
    2. Default Notebooks: Journal, Playground.
    3. My Notebooks: user-created writable notebooks.
    4. Seed Notebooks (Read-only): imported community and custom package notebooks, badged with a lock/seed indicator.

5.2 The `/notebooks` Page (Replacing `/catalogs`)

Unlike `/catalogs` today—which shows an empty-library warning banner until a remote seed is synced—the `/notebooks` page is immediately useful on first boot because Journal and Playground are always present, and users can create new notebooks offline at any time.
