Sound Handling — Current Architecture
Scope: how sound is produced, routed, and (not) played today. Sources: packages/lang/src/runtime/ (behaviors, strategies, metrics), apps/playground/src/services/audio/, apps/playground/src/contexts/AudioContext.tsx, apps/playground/src/hooks/useWorkbenchRuntime.ts, apps/playground/src/services/cast/rpc/. All claims verified against the working tree at commit 3bb30961.

1. Verdict

Sound is implemented twice, in two disconnected halves. Both halves work in isolation; they never meet. Every audible sound in the product today comes from a UI click — not from the workout runtime.

The broken link

The runtime emits sound cues correctly as SoundMetric outputs on emitOutput('system', …). Nothing in the app subscribes to those outputs to play audio. The one code path that would bridge runtime → audio is a runtime event ('sound:play') whose only producer, PlaySoundAction, is never constructed anywhere in the repository.

Net effect: the workout runtime's countdown beeps, completion cues, and interval alerts are silent. The compliance tests that assert "a sound output was emitted" pass, because they assert on metric presence, never on audible playback.

1.1 The two halves

HALF A — runtime cue production packages/lang
Compiler strategies → SoundCueBehavior → SoundMetric → emitOutput('system')
✔ works — ticks fire, metrics are emitted (43/43 compliance tests pass)
 
HALF B — audio synthesis apps/playground

✔ works — oscillators, envelopes, master gain all fine
 
THE BRIDGE

'sound:play' event ──▶ audioService.playSound() ✖ no producer
(PlaySoundAction is never constructed; not even exported from the engine barrel)

2. Half A — runtime cue production

The language runtime decides when a sound should fire and what it is called. It never touches an audio API.

2.2 The cue behavior

SoundCueBehavior (packages/lang/src/runtime/behaviors/SoundCueBehavior.ts) is the single runtime sound emitter. It has three trigger points:

Remaining-seconds math is hand-rolled inside the behavior rather than reusing calculateElapsed() from packages/lang/src/runtime/time/calculateElapsed.ts — it re-implements the span-sum inline at lines 78–85. The canonical helper exists and is used by CountdownTimerBehavior; the sound path duplicates it.

Dead code

packages/lang/src/runtime/models/SoundModels.ts and packages/lang/src/runtime/utils/soundUtils.ts define a second, incompatible cue model: SoundCue { id, threshold, sound, volume } with a threshold-based (not trigger-based) contract, plus PREDEFINED_SOUNDS and createCountdownSoundCues() / createCountUpSoundCues(). Nothing imports soundUtils; SoundCueBehavior defines its own local SoundCue interface instead. The two types are exported from the same barrel under the same name — SoundCue means the dead one.

5. Delivery channels

5.1 Local

Straightforward: AudioContext.playSound() → audioService.playSound() → WebAudioSink.

5.2 Chromecast

The cast path has its own event channel, and the runtime is not on it.

└─▶ castTransport.send({ type: 'rpc-audio', name, volume })
└─▶ receiver ReceiverSessionManager.ts:136 → audioService.playSound() ✔ works

└─▶ ✖ receiver never subscribes to outputs and never plays them

So the receiver receives sound metrics but treats them as inert data. The receiver's only audio input is rpc-audio, which the runtime never sends.

6. Defects found

6.1 Toggle confirmation beep never plays

AudioContext.tsx:47-55 calls audioService.playSound('beep') inside toggleAudio, but the audioService.setEnabled(isEnabled) sync lives in a useEffect that runs after the click handler. AudioService.playSound() returns early on if (!this.enabled) return; — and the service is still disabled at that instant.

Verified empirically with a probe that mocked audioService and reproduced the real gate: after clicking to enable, playSound was called with the service still disabled and produced no note. The user gets silence when turning sound on — the exact moment a confirmation would matter most.

6.2 Runtime cues are silent

The headline defect, detailed in §1. Root cause is a design split: SoundCueBehavior emits outputs (a data channel), while the app listens for events (a command channel). The output channel has no audio consumer; the event channel has no producer.

6.3 Name vocabularies are disjoint

Detailed in §3.2. Latent today, immediately fatal the moment the bridge is wired — every cue would become the same beep.

6.5 Test coverage asserts the wrong thing

Every sound test asserts metric presence, never audible playback:

  • apps/playground/tests/runtime-compliance/timer.compliance.test.ts:322-353 — asserts a sound-type metric exists with trigger === 'complete' and countdown atSecond values 3, 2, 1.
  • Equivalent assertions in amrap.compliance.test.ts:629-661, emom.compliance.test.ts:169-207, jit-compilation/forced-timer.test.ts:106-114.

These are green today and would stay green with the playback path entirely deleted. Nothing in the suite would notice that the product is silent. A future bridge must be tested at the playback boundary — e.g. drive AudioService with a RecordingAudioSink and assert the resolved notes, which would have caught both the missing bridge and the name mismatch.

7. The shape of the current design

What the code is actually asking for, independent of the fix:

  • Runtime owns semantics, app owns synthesis. The runtime correctly decides what happened and when; the app correctly knows how to make a tone. The split is right. Only the seam between them is missing.
  • Sound needs a single owner for names. Three vocabularies exist today (AudioPolicy, runtime cue names, PREDEFINED_SOUNDS) and none is authoritative. A cue name should resolve in exactly one place, and an unmapped name should be a loud, visible error rather than a silent fallback to beep.
  • Output vs. event. The runtime's system output channel is a good fit for recording a cue that fired (it already lands in analytics and the cast channel), but a poor fit for commanding playback at a precise moment. A cue needs both: a recorded fact and an immediate trigger.
  • Volume is per-call only. playSound(name, volume) takes a scalar, but there is no global user volume setting — the Settings page offers on/off only, despite the "Audio bell toggle & volume indicator" described in docs/abstract-views/.
  • The WebAudioSink envelope is fixed. Gain ramps from volume × 0.5 down to 0.01 over the note duration. There is no attack, no per-cue timbre beyond oscillator type, and no sample/asset path — every sound is synthesized.

8. The request, broken down

A target design, stated in terms the codebase can be checked against. Everything below is intent, not current behaviour — §9 is the gap analysis.

8.1 Core concepts

ConceptDefinition
Sound profileA named, user-defined set of rules describing which sounds fire and when, relative to a block's own duration. Profiles are defined in Settings and are the unit of selection.
Profile ruleOne trigger within a profile: an offset notation (:00, -:03, …) plus the sound to play at that point.
Default profileThe profile applied when no profile is selected. Always defined; falls back to the default profile.
Profile selectionA tag of the form sound-{profile}. On a note it selects the profile for the whole note; on a line/block it selects the profile for that block only.

8.2 Rule notation

Rules reuse the language's existing duration notation, with a leading : or - selecting the anchor:

NotationMeaningExample
:00Start of the block.A profile that opens with a horn at :00.
-:00End of the block.A profile that finishes with a bell at -:00.
-:03, -:02, -:01Seconds remaining, counted back from the end.The classic 3-2-1 countdown is three rules: -:03, -:02, -:01.
:05:00Elapsed time from the start — a sound 5 minutes into a 5:00 block. The magnitude accepts every duration spelling: 00:05:00, 05:00 and 5:00 all mean the same offset.A mid-workout mark.

Two families, distinguished by the sign: anchored to the start (:…, elapsed) and anchored to the end (-:…, remaining). A rule's offset is relative to the block's own duration, so one profile works for any block length.

8.3 Selection and precedence

Three levels, most specific wins:

1 Block level — a sound-{profile} tag on a line selects the profile for that block only.
2 Note level — a sound-{profile} tag on the note selects the profile for every block in the note.
3 Default — no selection anywhere → the default profile applies.
 
note tag ──▶ compile-level resolution ──▶ default profile
block tag ──▶ overrides the note-level choice for that one block

The note-level tag is resolved at compile level, not at runtime — the compiler already knows the note, so the resolution is a compile-time decision and needs no runtime lookup.

8.4 What the runtime must do

Given a block and the profile resolved for it, the runtime subscribes to the right event triggers and plays the right sound for each rule:

profile rules ──▶ SoundCueBehavior (or successor)
├─ :00 ──▶ subscribe mount ──▶ play
├─ -:00 ──▶ subscribe unmount ──▶ play
├─ -:03/-:02/-:01 ──▶ subscribe tick (bubble) ──▶ play at each remaining second
└─ :05:00 ──▶ subscribe tick (bubble) ──▶ play when elapsed reaches 5:00
 
cue fires ──▶ emit SoundMetric (record the fact) and trigger playback (act on it)

The rule's sound name is carried on the metric, so the same resolution path that records the cue is the one that plays it. A profile's rule names a sound; that name must resolve against the same authoritative sound table the app uses — not the current disjoint vocabularies of §3.2.

9.2 Where the work concentrates

Two clusters, plus one cross-cutting decision:

  • Compile-side resolution (mostly new): profile storage → rule parsing → note-level tag → compile-level selection → per-block profile. The pieces that make this feasible already exist — the settings convention, the tag-type registry, and analyticsOptions.userProfile as precedent for compile-time user data. What does not exist is the path from note tags into the compiler.
  • Runtime-side generalization (mostly extending): SoundCueBehavior already does mount / tick / unmount and countdown de-duplication. It needs rules as data instead of hardcoded cues, plus an elapsed-relative trigger for :05:00-style rules.
  • Cross-cutting — the one vocabulary decision. Everything above converges on a single question: what is a sound called? Until one table owns the names, profiles will resolve to strings that playback cannot honor, and the existing silent-fallback will hide it. This is the same defect as §3.2 and §6.3, seen from the profile angle.

9.3 Resolved design decisions

Points where the request as stated left a choice open, and the answers now given:

  • Does a profile select sounds or trigger points? Both. Each trigger point defines the sound it generates, so a rule is "offset + sound name" and the profile fully determines both when and what.
  • Is the block-level selection a tag or the existing property? Parser-level tag references. A tag reference is written #tag-slug and used as a property value; tags are marked down with the metrics they add, so a tag can contribute a sound selection. Several references can be stacked on one line — sound: #sound-classic #sound-loud — and each contributes.
  • Does the note-level tag override a block-level one, or merge? Strict precedence, no merge. The note level overrides the default, and the line level overrides the note level.
  • What happens to a rule whose offset exceeds the block's duration? It never fires. The rule is dropped when the profile is resolved against the block's duration — no warning, no error.
  • Does the profile replace the existing per-strategy cues (countdown-beep, timer-complete, …), or coexist with them? Replaced. A generic sound behavior loads the profile's rules and sends sound events at the trigger points; the per-strategy hardcoded cues are gone.

Two further consequences worth recording. First, the trigger magnitude accepts every duration spelling the language already understands — :05:00, :00:05:00, :5:00 and :300 are the same offset. Second, a rule's offset is relative to the block's own duration, so one profile works for any block length.
