Code review · Chromecast sender stack

Chromecast on mobile vs desktop: why the phone stops feeding the TV

The desktop cast works. On a phone the receiver never reflects the browser's state. This review maps the sender→receiver path in apps/playground/src/services/cast/** and the receiver app in apps/playground/app/receiver-rpc.tsx, isolates every point where a phone browser behaves differently from a desktop browser, and ranks the causes with a triage runbook and concrete fixes.

Scope cast sender + receiver Repo wod-wiki Reviewed 2026-10-22 Method static read of live code Head f8520d9d7

Status update — 2026-10-22: the control-plane fixes have landed

Three findings are now fixed in code and covered by tests (13 new handshake/config tests; full playground suite 2962 pass / 0 fail): F5 — TURN relay support via VITE_CAST_TURN_URL/VITE_CAST_TURN_USERNAME/ VITE_CAST_TURN_CREDENTIAL in services/cast/config.ts, consumed by WebRtcRpcTransport; F6 — the offerer now retransmits its offer every 1 s until the answer arrives, the receiver broadcasts cast-ready on CAF READY to trigger an immediate resend, and duplicate offers/answers are ignored; and new finding F13 below — the receiver-side race that made every one of those offers moot. Not fixed yet: F1 (iOS has no Cast Web Sender SDK — needs a native wrapper or Android), F2–F4 (wake lock / pagehide / background freeze — sender-side lifecycle work), F7 (only the diagnostics half: the timeout error now reports signaling/ICE state and gathered candidate counts), F8–F12.

1. Verdict

The cast stack contains no mobile-specific code at all

A search of apps/playground/src/services/cast/** and apps/playground/src/components/organisms/cast/** for userAgent, isMobile, isIOS, isAndroid, visibilityState, document.hidden, pagehide and requestAnimationFrame returns no platform branch anywhere in the cast path. The only isMobile in the app is layout (Workbench.tsx:280, HistoryLayout.tsx:37).

Every behaviour the stack relies on is therefore an unstated desktop assumption: a foreground tab, a secure origin, a LAN that also carries the Chromecast, a radio that does not migrate, and a device that never sleeps mid-workout. A phone breaks five of those five.

There are two independent legs between the phone and the TV, and they fail differently:

  • Control plane — the Google Cast SDK session carries the WebRTC offer/answer/ICE over the custom namespace urn:x-cast:com.wodwiki.
  • Data plane — all workout state flows over an RTCDataChannel named wod-wiki-rpc.

If the control plane never completes, the TV stays on “waiting-for-cast” forever. If the data plane opens but the phone stops pushing, the TV shows a stale workout. Both look like “the Chromecast state doesn't update”, so the first job is to tell them apart — the runbook in §6 does that in about ten minutes.

Read this first

If the phone in question is an iPhone, F1 is the answer and none of the others matter: Google's own documentation states that the Web Sender SDK is supported on Mac, Windows, Linux, ChromeOS and Android, and that iOS requires a native Cast app. The code in this repo cannot make casting work on iOS — it would need the native Google Cast iOS SDK, or a different transport (a relay server) that does not depend on the Cast SDK at all.

On Android, F2/F3/F4 are the realistic causes and they compound: the phone sleeps (F2), the page freezes (F4), and the freeze can trip pagehide (F3) and kill the receiver session.

The push chain, hop by hop

Every state change the user makes in the phone browser travels this path. The rightmost column is where a mobile browser can go quiet.

# Hop Where Trigger Mobile risk
1 Runtime action → stack snapshot ScriptRuntime.ts:164, :182 → RuntimeObservers.emitStack User action (event-driven, no timer) Low — but only while the page runs
2 Snapshot → cast subscription SubscriptionManager.ts:28-37 → ChromecastRuntimeSubscription.ts:42 Observer fan-out Low
3 Subscription → transport ChromecastRuntimeSubscription.ts:56 → WebRtcRpcTransport.ts:110 Direct call Medium — silently dropped if the channel is not open
4 Transport → wire WebRtcRpcTransport.ts:116 dc.send(...) DataChannel High — radio migration / sleep kills the channel
5 Wire → receiver runtime WebRtcRpcTransport.ts:271 → ChromecastProxyRuntime.ts:386 DataChannel High — same
6 Clock snapshot (separate path) useLiveClockAuthority.ts:89 → clockCommands.ts:148 → CastButtonRpc.tsx:252 React re-render triggered by hop 1 High — a frozen tab never re-renders
7 Workbench mode WorkbenchCastBridge.tsx:26-53 Zustand selector change High — plus a fingerprint guard that skips re-sends

The structural weakness: every push is a one-shot, no replay

Hop 3 drops the message when the channel is closed (WebRtcRpcTransport.ts:112-113, “DataChannel not open — dropping message”). Hop 7 skips a send when the fingerprint is unchanged. Hop 6 is documented as “No replay queue — a send that fails is dropped; the next snapshot or reconnect resyncs” (CastButtonRpc.tsx:236-237).

On a desktop the channel is stable, so a dropped message is rare. On a phone the channel drops whenever the radio migrates or the screen locks, and the next snapshot may never come — the user is left holding a TV that shows the wrong workout with no error anywhere.

4. Findings

F1The Cast Web Sender SDK is not supported on iOS

Blocker Applies to: iPhone / iPad Confidence: high — vendor-documented

Evidence

The sender loads the CAF Web SDK and drives the Framework API: ChromecastSdk.ts:133 injects cast_sender.js?loadCastFramework=1; ChromecastSdk.ts:150-156 calls cast.framework.CastContext.getInstance().setOptions(...); ChromecastSdk.ts:196 calls ctx.requestSession(). Google's Web Sender documentation states that the SDK “is supported on Cast-supported web browsers on Mac, Windows, Linux, ChromeOS, and Android devices”, and that iOS needs a native Cast app (Android Apps / iOS Apps sender SDKs).

Why mobile differs

On iOS the SDK either never initialises (__onGCastApiAvailable(false) → ChromecastSdk.ts:117-118 sets state unavailable) or loads but cannot discover/attach to a device. Either way ChromecastBackend.ts:129-131 throws “Cast not supported in this browser”, and CastButtonRpc.tsx:326-332 renders a permanently disabled button. Nothing in this repository can change that.

Confirm in one line

// in the phone's console, on the casting page
!!window.cast?.framework   // false ⇒ the sender SDK never initialised
window.isSecureContext     // false on http://<LAN-IP>:port

Fix options

  • Native iOS sender — ship the Google Cast iOS SDK in a native shell. Full support, but a new app surface.
  • Drop the Cast SDK dependency on mobile — replace the discovery/control plane with a relay (the receiver app already tolerates a relay URL, see config.ts and the relay=ws://… receiver convention), so a phone only needs a browser and a WebSocket. This also fixes F3–F8 in one move, because the data plane would no longer depend on the phone's WebRTC stack or page liveness.
  • Declare the limitation — detect an unsupported sender and say so on the button instead of rendering a dead control.

F2The wake lock is a no-op on the phone, so the screen sleeps and the page freezes

High Applies to: any phone Confidence: high — code + platform spec

Evidence

CastButtonRpc.tsx:80 calls useCastWakeLock(isCasting). The hook resolves the API with useCastWakeLock.ts:29: if (!('wakeLock' in navigator)) return undefined;, and :40 bails out when the API is missing. The Screen Wake Lock API is secure-context only (MDN: “This feature is available only in secure contexts (HTTPS)”), and it is additionally gated by the screen-wake-lock Permissions-Policy.

Why mobile differs — this is the sharpest desktop/mobile delta in the repo

  • Desktop dev serves http://localhost:5173. http://localhost is a potentially trustworthy origin, so it is a secure context → the wake lock is granted → the desktop stays awake → the push path keeps running.
  • A phone cannot use localhost; it loads http://192.168.x.x:5173, which is not a secure context → navigator.wakeLock is undefined → useCastWakeLock returns immediately → the phone dims and locks after the OS timeout.
  • Once the screen locks, the mobile browser suspends the page: timers throttle, requestAnimationFrame stops, React stops re-rendering. The push chain in §2 is entirely event-driven off React and the runtime, so nothing is pushed any more.

Confirm

window.isSecureContext            // false ⇒ wake lock unavailable
'wakeLock' in navigator         // false ⇒ hook no-ops
// then lock the phone: console stops logging and the TV stops updating

Fix options

  • Serve the phone over HTTPS (or add https:// dev cert / tunnel). Cheap, restores the wake lock, and is required by Google for the remote-display path anyway.
  • Detect and warn — if the wake lock is unavailable, show “keep this tab open; the TV will go stale if your screen locks”. The hook already swallows the failure silently (useCastWakeLock.ts:57-59).
  • Stop depending on the phone being awake — see F4. The receiver already interpolates elapsed time from spans, so the TV timer survives a frozen sender; only state changes are lost.

F3pagehide tears the receiver down — and mobile fires it on backgrounding

High Applies to: iOS strongly, Android possibly Confidence: medium-high — code + platform behaviour

Evidence

CastButtonRpc.tsx:263-272 registers window.addEventListener('pagehide', onPageHide), and onPageHide calls sessionManager.sendDisposeSignal() (CastSessionManager.ts:196-199), which sends { type: 'rpc-dispose' } over the data channel. On the TV, ChromecastProxyRuntime.ts:386-391 handles rpc-dispose by disposing the transport and the whole proxy runtime, and receiver-rpc.tsx:487-499 resets to the waiting screen.

Why mobile differs

On desktop, pagehide fires when a tab is closed or navigated away — a real end of session. On mobile the lifecycle is different: switching apps or locking the screen moves the page to hidden and eventually fires pagehide when the page is frozen or discarded (iOS in particular). The result is that a momentary trip to the home screen can permanently reset the TV back to “waiting-for-cast”, even though the phone still believes it is casting.

Confirm

// phone console, then background the app for ~10s and return
[CastButtonRpc] ... (no log — add a temporary console.log in onPageHide)
// TV console (chrome://inspect):
[ReceiverApp] RPC transport disconnected — returning to waiting screen

Fix options

  • Do not send rpc-dispose on pagehide — the receiver already detects the DataChannel closing and resets itself. The polite signal is redundant and, on mobile, harmful.
  • Gate on visibilityState — only dispose on a real unload (beforeunload / pagehide with event.persisted === false and a short grace period).
  • Re-adopt on return — the code already re-adopts a session that outlives the mount (CastButtonRpc.tsx:175-197, ChromecastBackend.resumeSession()). Make sure a visibilitychange → visible handler triggers the same path, so a backgrounded phone re-attaches instead of leaving the TV blank.

F4A frozen mobile page suspends the whole push path

High Applies to: any phone Confidence: high — code + platform behaviour

Evidence

The state path has no timer of its own: runtime actions emit snapshots (ScriptRuntime.ts:164, RuntimeObservers.emitStack), the subscription manager fans them out (SubscriptionManager.ts:28-37), and ChromecastRuntimeSubscription.ts:42 sends them. The clock snapshot is derived from a React re-render (useLiveClockAuthority.ts:89-92 → useClockController.ts:57-60 → clockCommands.ts:148-160 → CastButtonRpc.tsx:259). The only setTimeout users are ClockSync.ts:96 and ClockSync.ts:180.

Why mobile differs

A frozen page executes none of it. iOS Safari and Android Chrome both suspend backgrounded pages — timers throttle, rendering stops, and the page may be discarded entirely, tearing down the DataChannel with it. A desktop tab that is merely hidden keeps its socket and keeps rendering (throttled, but alive), which is why the desktop appears unaffected.

The receiver is not fully blind to this: it interpolates elapsed time from the spans it already has, so the on-screen timer keeps counting. What stops arriving is state — the next block, a new workout, rep entries, the mode change. That matches the reported symptom precisely: the TV shows a workout, but it never reflects the phone's latest events.

Fix options

  • Move the authority to the TV — the receiver already holds a proxy runtime and interpolates time; letting it own the workout progression makes the sender a pure UI. Largest change, correct architecture.
  • Heartbeat + staleness indicator — send a periodic rpc-heartbeat; the receiver shows “sender asleep” after N missed beats instead of silently showing stale data. Small, and it converts an invisible failure into a visible one.
  • Re-sync on resume — on visibilitychange → visible, force a full resend (stack snapshot + workbench mode + clock snapshot) rather than waiting for the next natural change.

F5No TURN relay — the WebRTC leg only works on one LAN

High Applies to: any phone off the TV's LAN Confidence: high — code is unambiguous

Evidence

WebRtcRpcTransport.ts:55-59 is the entire ICE configuration: 

this.pc = new RTCPeerConnection({
    iceServers: [
        { urls: 'stun:stun.l.google.com:19302' }
    ]
});

A repository-wide search for turn: / turns: returns no matches. STUN only discovers a public reflexive address; it cannot relay. With no TURN server, the only viable candidates are host/mDNS addresses, which are reachable only inside the same broadcast domain.

Why mobile differs

A desktop sits on the office/home Wi-Fi, the same segment as the Chromecast, so host candidates connect directly. A phone is frequently on cellular (the Chromecast's private address is unroutable and the carrier-grade NAT is not inbound-reachable) or on a guest/isolated VLAN.

Important nuance: Cast device discovery also needs the local network, so a phone that can see the Chromecast in the picker is usually already on the same LAN. Treat F5 as a hit when the phone is on a different Wi-Fi than the TV, on a guest network, or when the phone briefly drops to cellular (Wi-Fi assist, dead-zone handover) — that last case is the nastiest, because the session dies mid-workout and the code does not re-establish it.

Confirm

// phone console during connect():
[WebRtcRpcTransport:offerer] ICE candidate (local): ...
[WebRtcRpcTransport:offerer] TIMEOUT after 15000ms — pcState=…, iceState=…, dcState=connecting

Fix options

  • Add a TURN server (coturn) with credentials from env: { urls: 'turn:turn.example.com:3478?transport=udp' } plus a turns: entry on 5349. Keep iceTransportPolicy: 'all' so LAN peers still connect directly. This is the standard fix and the only one that survives cellular.
  • Surface ICE diagnostics — the candidate log is truncated to 60 characters and the failure reason is never shown. Log the full candidate list and the ICE failure reason; it is the difference between a 5-minute and a 5-hour diagnosis.
  • Move to a relay transport for mobile — see F1.

Status (2026-10-22)

Fixed buildIceServers() in apps/playground/src/services/cast/config.ts assembles CAST_ICE_SERVERS: Google STUN by default (or VITE_CAST_STUN_URL), plus a TURN entry with username / credential when VITE_CAST_TURN_URL is set. The transport now constructs its RTCPeerConnection from that list, and the connect-timeout error reports how many local ICE candidates were gathered — the F5 “surface ICE diagnostics” half is covered too.

F6The WebRTC offer is sent once, fire-and-forget

High Applies to: any phone Confidence: high — code is unambiguous

Evidence

CastSignaling.ts:58-66: 

send(signal: WebRTCSignalMessage): void {
  this.session
    .sendMessage(CAST_NAMESPACE, signal)
    .then(() => console.log(`… sendMessage(${signal.type}) OK`))
    .catch((err) => console.error(`… sendMessage(${signal.type}) FAILED`, err));
}

There is no queue, no retry, no timeout, and the failure is only logged. The offer itself is sent exactly once, from WebRtcRpcTransport.ts:200-208, immediately after requestSession() resolves (ChromecastBackend.ts:146-157) — i.e. potentially before the TV's receiver app has loaded and called castContext.start() to register the namespace (receiver-rpc.tsx:588-597). The receiver only starts listening for offers after that (receiver-rpc.tsx:626-631).

Why mobile differs

The receiver app is a web page fetched over the internet by the Chromecast; its boot has a 12 s budget (receiverBootLoader.ts:1, RECEIVER_BOOT_READY_TIMEOUT_MS = 12000). The phone's radio and CPU are slower than the desktop's, so the window in which a one-shot offer can be lost is much wider.

Confirm

// phone:                         TV (chrome://inspect):
[SenderCastSignaling] Sending: webrtc-offer   (no matching)
[SenderCastSignaling] sendMessage(webrtc-offer) OK
                                          ← offer never arrived ⇒ sender sent too early

Fix options

  • Application-level readiness handshake — the receiver announces cast-ready on CAF READY (receiver-rpc.tsx:605-612); the sender waits for it before offering. This is the clean fix and removes the guesswork.
  • Retry the offer — re-send the offer on a short interval (say every 500 ms, up to the connect deadline) until the DataChannel opens. The receiver already handles a repeated offer gracefully: setupTransport() disposes the old session and starts fresh (receiver-rpc.tsx:531-563).
  • Queue signalling sends — buffer SDP/ICE until the sendMessage promise resolves, and surface a rejected send as a user-visible error rather than a console line.

Status (2026-10-22)

Fixed Options 1 and 2 are both implemented in WebRtcRpcTransport: the offerer retransmits its offer on a 1 s interval (configurable via offerRetryIntervalMs) until the answer arrives or the connect deadline hits, and the receiver broadcasts { type: 'cast-ready' } on CAF READY, which makes a waiting offerer resend immediately. Duplicate offers with identical SDP and duplicate answers once stable are ignored, so the retransmits are safe.

Correction to the second option above: the claim that “the receiver already handles a repeated offer gracefully” was wrong in a way that mattered — setupTransport() builds a new transport that subscribes to the signaling bus after the repeated offer was dispatched, so the retry copy would have been lost exactly like the first. See F13 below; the retry only works because the triggering offer is now injected into the new transport directly.

F7A 15 s connect budget competes with a 12 s receiver boot

Medium Applies to: any phone Confidence: medium-high

Evidence

WebRtcRpcTransport.ts:170 — connect(timeoutMs = 15_000). Both ChromecastBackend.startSession() (ChromecastBackend.ts:157) and resumeSession() (ChromecastBackend.ts:203) use the default. The timeout rejects with “WebRTC connect timed out after 15000ms” (WebRtcRpcTransport.ts:180-181), and the failure path resets the button to ready (ChromecastBackend.ts:159-169).

Why mobile differs

The 15 s budget covers the whole handshake — ICE gathering, the Cast message round trip, the TV's boot, and the DataChannel open — and the TV's boot alone is allowed 12 s. On a phone that also has to warm up a radio and a slower CPU, the budget is not realistic. There is no progress indication: the button shows “Connecting…” for 15 s and then fails with no explanation (CastButtonRpc.tsx:293-307 logs, and shows nothing).

Fix options

  • Make the deadline adaptive (e.g. 45 s) and log the phase that consumed it.
  • Show a live “waiting for the TV…” / “negotiating…” state instead of a spinner.
  • Pair with F6: the readiness handshake means the 15 s only has to cover ICE, not the TV's boot.

F8Dropped sends are never replayed

Medium Applies to: any phone Confidence: high

Evidence

  • WebRtcRpcTransport.ts:110-118 — send() logs “DataChannel not open — dropping message” and returns.
  • ChromecastRuntimeSubscription.ts:43 — if (!this.transport.connected) return;, and the fingerprint at :50-53 means an unchanged state is not re-sent.
  • WorkbenchCastBridge.tsx:33-35 — same fingerprint guard. If the very first workbench message is lost, the TV sits on the waiting screen until the user changes something.
  • CastButtonRpc.tsx:236-237 documents the policy explicitly: “No replay queue — a send that fails is dropped; the next snapshot or reconnect resyncs.”

Why mobile differs

The DataChannel is momentarily closed far more often on a phone: radio handover, screen lock, app switch, or the ICE connection re-checking. Each of those produces a silent gap in the state stream.

Fix options

  • Keep the last message per type and flush it in onConnected.
  • On onDisconnected → onConnected, force a full resync (stack + workbench + clock) instead of waiting for the next natural change.
  • Count drops and surface “reconnecting…” in the UI.

F9Clock sync silently dies above 500 ms RTT, so the TV clock drifts

Medium Applies to: any phone Confidence: high

Evidence

ClockSync.ts:73-74: 

const samples = this.options.samples ?? 3;
const maxRtt  = this.options.maxRttMs ?? 500;

A sample with RTT above 500 ms is discarded (ClockSync.ts:150-152); if all three are discarded, sync() throws “Clock sync failed: all samples exceeded max RTT” (ClockSync.ts:101-103) and sendResult() never runs (ClockSync.ts:117-127), so the receiver never receives rpc-clock-sync-result and keeps a zero offset. The caller swallows the error: CastSessionManager.ts:177-181 — clockSync.sync().catch(err => rpcError(...)), “best-effort: don't block connect()”. The per-sample response timeout is also only 2 s (ClockSync.ts:159).

Why mobile differs

Desktop-on-LAN RTT is single-digit milliseconds. Cellular RTT routinely exceeds 500 ms, and a congested Wi-Fi link can too. The failure is silent: the only trace is a console warning.

Impact

The TV's elapsed-time display drifts from the phone's by the sender/receiver clock skew, and — because the receiver subtracts a zero offset — by the accumulated RTT asymmetry. The workout itself is unaffected; the displayed time is.

Fix options

  • Raise the ceiling (e.g. 2000 ms) and use a median of more samples.
  • Report the failure: log the measured RTT, and warn in the UI that the TV clock is unsynchronised.
  • Re-sync periodically, not only once at connect — the network path changes on mobile.

F10No capability probe, no diagnostics, no error the user can see

Structural Applies to: all Confidence: high

Evidence

  • No platform branch exists anywhere in the cast path (see §1).
  • Every failure is a console.log/console.error inside the transport (WebRtcRpcTransport.ts:63,113,180), the SDK wrapper (ChromecastSdk.ts:117,200) or the button (CastButtonRpc.tsx:296-302). The user sees the button return to idle and nothing else.
  • The SDK exposes exactly two states that matter to the UI — unavailable and session-active (ChromecastBackend.ts:38-44). There is no degraded, stale, or reconnecting state, so every partial failure collapses into “not casting”.

Why it matters on mobile specifically

A mobile failure has many more causes than a desktop one (F1–F9), and the sender is in the user's hand, not next to the TV. Without a visible signal (“the Cast SDK is unavailable on this browser”, “the TV hasn't responded”, “this phone's screen is locked — the TV may be stale”), every occurrence looks identical from the user's seat.

Fix options

  • Introduce a CastEnvironment probe: secure context, navigator.wakeLock, navigator.connection, platform, Cast SDK availability — computed once and logged.
  • Extend ICastBackendState with degraded/reconnecting and render it on the button.
  • Add a “Cast diagnostics” panel in the browser: session id, ICE state, candidate pairs, DataChannel state, last send/receive timestamps, clock-sync RTT.

F11 · F12Two smaller robustness defects

Low Applies to: all

F11 — SDK reload after a failed first load hangs forever

ChromecastSdk.load() clears its memo on failure ChromecastSdk.ts:96-104) but _load() refuses to re-inject the script if the tag is already in the DOM (ChromecastSdk.ts:135): if (!document.querySelector(...)) { … } — “If the script tag already exists the callback will fire on its own.” It will not: the SDK has already run and already called __onGCastApiAvailable. The retry therefore waits on a promise that can never settle. A single blocked or truncated script fetch on a flaky mobile network bricks every subsequent cast attempt until the page is reloaded.

F12 — window.chrome read without a guard

ChromecastSdk.ts:150-156 destructures const { cast, chrome } = window; and then reads chrome.cast.AutoJoinPolicy.ORIGIN_SCOPED. If window.chrome is undefined in the browser, that throws, the catch at ChromecastSdk.ts:122-128 sets the state to unavailable, and the SDK is declared unsupported even though it loaded fine. A one-line optional chain fixes it.

Fix

  • F11: remove the stale <script> tag before re-injecting, and add a load timeout so a missing callback rejects instead of hanging.
  • F12: autoJoinPolicy: chrome?.cast?.AutoJoinPolicy?.ORIGIN_SCOPED ?? 'origin_scoped'.

F13The offer that rebuilds the receiver transport never reaches it

Blocker Applies to: any phone, first cast after receiver boot Confidence: high — code is unambiguous Fixed 2026-10-22

Evidence

In apps/playground/app/receiver-rpc.tsx the shared signaling listener dispatches an incoming webrtc-offer to its subscribers and then calls setupTransport(). setupTransport() constructs a brand-new WebRtcRpcTransport, whose constructor subscribes to the signaling bus — but that dispatch has already happened. The new answerer sits in connect() waiting for ondatachannel; the one offer that would make it answer was processed by zero transports. Fifteen seconds later connect() times out and the receiver shows an error.

Why desktop worked anyway

Two masks, both timing-dependent. (a) A warm Chromecast keeps the receiver app alive (disableIdleTimeout: true), and the leftover transport from a previous session was never disposed on disconnect — it stayed subscribed and would answer the next offer, so repeat desktop casts connected through an orphan. (b) The first desktop attempt after a receiver reboot had the same race, but a desktop retry (button re-click seconds later) landed while the orphan from attempt one was still listening. A phone casting for the first time after the TV boots hits the race raw: no orphan exists yet. (Masking mechanism inferred from the pre-fix dispose path; the dispatch-before-subscribe ordering is verified code fact.)

Fix

  • setupTransport(trigger) now takes the offer that caused the rebuild and injects it into the fresh transport via the new WebRtcRpcTransport.receiveSignal(trigger) — the same queued path live signals use, so ordering is preserved.
  • The orphaned-transport leak is closed: the receiver session is created with disposeTransportOnDisconnect: true (ReceiverSessionManager), so a dead transport no longer stays subscribed and steal the next offer's answer.
  • Covered by src/services/cast/rpc/__tests__/WebRtcRpcTransport.handshake.test.ts (answerer consumes an injected offer; duplicate/changed-offer guards; retry, cast-ready, and dispose semantics).

Residual risk

The duplicate-offer guard compares raw SDP strings, so an offer whose SDP differs only in ICE credentials re-triggers a full renegotiation on the existing transport instead of being treated as a duplicate. Harmless for the current one-shot-per-session design; revisit if renegotiation is ever added.

6. Triage runbook (≈10 minutes, on the phone)

Run this before changing any code. It separates the control plane from the data plane and identifies which finding you are actually hitting.

  1. Establish the platform. iOS or Android? If iOS, stop here — F1 applies and no code change in this repo will help. Confirm in the phone console with !!window.cast?.framework.
  2. Establish the origin. Read location.origin and window.isSecureContext on the phone. If the origin is http://192.168.x.x:… and isSecureContext is false, F2 is live: the wake lock cannot work and the screen will sleep mid-workout.
  3. Watch the cast handshake. Click the Cast button and read the phone console:
    • [Cast SDK] Initialised with App ID: … — SDK OK.
    • [Cast SDK] Not available: … — F1/F12.
    • [SenderCastSignaling] sendMessage(webrtc-offer) FAILED — the Cast bus rejected the offer.
    • [WebRtcRpcTransport:offerer] DataChannel OPEN in …ms — control plane OK, go to step 4.
    • [WebRtcRpcTransport:offerer] TIMEOUT after 15000ms — the handshake failed: F5 (ICE) or F6 (offer lost).
  4. Check the TV. Open chrome://inspect on the desktop and select the receiver. Look for [ReceiverApp] Received webrtc-offer — triggering transport setup. If the phone sent the offer but the TV never logged it, that is F6 (the receiver had not registered the namespace yet). If the TV logged it and still shows “waiting-for-cast”, the DataChannel never opened — F5.
  5. Check the data plane. With the DataChannel open, change something in the phone (select the next block) and watch the phone console for [WebRtcRpcTransport] DataChannel not open — dropping message. If it appears, F8 is compounding the problem.
  6. Test the freeze hypothesis. Lock the phone for 30 seconds, unlock it, and change state. If the TV does not update until you perform a new action (or the phone's console shows nothing while locked), F4 is confirmed. Check also whether the TV dropped back to “waiting-for-cast” — that is F3 (pagehide → rpc-dispose).
  7. Measure the RTT. Look for [ClockSyncService] Sample N/N: offset=… RTT=… in the phone console. If every sample says “failed (RTT exceeded max RTT)”, F9 is confirmed and the TV's clock is unsynchronised.

What to capture before filing the fix

Phone console export (including the lines above), the phone's location.origin and isSecureContext, whether the phone was on Wi-Fi or cellular, whether the screen locked during the test, and the TV's chrome://inspect console. Those five facts determine which of F1–F9 applies and close the issue on the first pass instead of the fourth.

7. Recommended sequence

  1. Diagnose (no code). Run §6 and identify the finding. Do not start with code — F1 and F5 need completely different work from F3 and F4.
  2. Cheap, certain wins. HTTPS on the phone (F2), stop sending rpc-dispose on pagehide (F3), guard window.chrome and fix the SDK reload hang (F11, F12), adaptive clock sync (F9).
  3. Make failures visible. Capability probe + degraded button states + a diagnostics panel (F10). Without this, every future mobile report is another ambiguous bug.
  4. Harden the session. Readiness handshake, offer retry, replay-on-reconnect, heartbeat (F4, F6, F7, F8).
  5. Decide the platform question. If iOS must be supported, choose between a native Cast app and a relay transport (F1). Both are large; the relay also retires F3–F8.

One design note worth taking from this

The receiver already interpolates elapsed time locally from the spans it holds, and it already owns a proxy runtime (ChromecastProxyRuntime.ts). The browser is being asked to be both the UI and the authority. On a desktop that is fine; on a phone it is asking a browser that is designed to be suspended to be the source of truth for a workout that is being shown on a television. Moving the progression authority to the receiver is the change that makes the whole class of findings disappear — and it is worth considering independently of this bug.

8. Answers to Open Questions & Ground Truth

These user-provided facts narrow the diagnosis to the exact broken link:

  1. Is the phone iOS or Android? Android — F1 (iOS Web Sender unsupported) is ruled out. Android Chrome is an officially supported CAF sender.
  2. Does the phone share a LAN with the Chromecast, and did it drop to cellular? Shares LAN, did not drop to cellular — F5 (cross-network NAT without TURN) is ruled out for initial connect. Both devices are on the same local network.
  3. What is the page's origin on the phone? https://wod.wiki — F2 (insecure origin disabling Wake Lock) is ruled out. Origin is fully secure context.
  4. Does the TV stay on “waiting-for-cast” or show a workout? Stays on connecting, then flashes disconnected — Ground truth! The session never successfully connects or establishes the WebRTC DataChannel. The connection handshake fails and times out or is torn down immediately.
  5. Does the screen lock during normal workout? N/A — user hasn't gotten that far because the connection never completes.
