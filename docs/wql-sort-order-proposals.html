Architecture & Language Design Spec

WQL Sort Order & Default Sort Order Proposals

Analysis of current sorting mechanics in Wod Query Language (WQL), identifying discrepancies between parser, QueryService execution, database pushdown, and UI layers, followed by three concrete architecture proposals to support explicit sorting and canonical default sort order contracts.

1. Executive Summary 2. Current State Audit & Asymmetries 3. Core Architectural Dilemmas 4. Proposal A: Pragmatic Standardized Pipes 5. Proposal B: Suffix Clause `sort by {}` 6. Proposal C: Two-Tier Relational Model 7. Storage Pushdown & Paging Spec 8. Lazy Senior Verdict & Phasing

1. Executive Summary

In WQL today, sorting is treated as an optional presentation pipe (| order by col [asc|desc]). While simple on the surface, this creates several severe architectural asymmetries across targets, execution engines, and UI consumers:

0 / 6
Targets with explicit default sort contract

WQL defines no target-level default sort orders. Results without | order by rely on incidental database insertion order or memory map order.

1 / 5
Targets actively ignoring order

:session silently ignores | order by with an advisory warning, hardcoding completion time descending regardless of user input.

Broken
Server paging & limit pushdown

Because default order is incidental id asc, queries like :journal{} | limit 20 slice the 20 oldest rows, requiring UI hacks to fix.

The Hidden Paging Bug: In packages/wql/src/QueryService.ts (line 279), server paging defaults to order: [{ field: 'id', direction: 'asc' }]. When an author writes :journal{} last 4w | limit 20, they expect the 20 most recent entries. Instead, the storage layer fetches the 20 lowest IDs. The playground UI masks this because entryGrouping.ts sorts client-side in React memory, but once collections exceed 100+ items, queries slice the wrong items before the UI ever sees them.

A line-by-line inspection of wql.grammar, wql.ts, QueryService.ts, stores.ts, and document.ts reveals an uneven landscape:

Code Evidence (packages/wql/src/QueryService.ts:1138-1145): 
// Current in-memory sorting reverses authored order to apply stable JS sort:
for (const order of [...(pipes?.order ?? [])].reverse()) {
  const dir = order.dir === 'desc' ? -1 : 1;
  records = [...records].sort((a, b) => {
    const av = a[order.col] ?? a.__id;
    const bv = b[order.col] ?? b.__id;
    if (av === bv) return 0;
    return ((av as number | string) > (bv as number | string) ? 1 : -1) * dir;
  });
}
If pipes.order is missing, records are never sorted by date or title—they remain in the raw storage array order.

3. Core Architectural Dilemmas

Before choosing a syntax or API, five core design questions must be resolved:

1. Pipe (`| order by`) vs Suffix Clause (`sort by {}`)

WQL currently uses | select | order by | limit as presentation pipes. But WQL also supports value pipelines (:journal{} | :count{} | :bar{}). Having pipe | represent both stage transformations and row shaping causes parser ambiguities and prevents presentation pipes between pipeline stages.

2. Target Default vs Global Default

Should default sort order be defined per target noun (e.g. :journal defaults to date desc, while :effort defaults to label asc), or should there be a universal default? The data proves a universal default fails: training journals need chronological descending, but exercise registries need alphabetical ascending.

3. Grouping vs Sorting Interaction

When a query contains both by {discipline} and order by date desc, what is sorted?
A) The shelves/groups (e.g., sort disciplines by most recent date)?
B) The rows inside each shelf?
C) Both?

4. Storage Pushdown vs In-Memory Slicing

Currently, authoring | order by forces paged: false in domainPaging, loading all notes into memory. As personal journals grow to thousands of notes, sorting in JS destroys performance. Default and explicit sort orders must push into SQLite/IndexedDB queries.

4. Proposal A: Pragmatic Standardized Pipes (Incremental Evolution)

Keep the existing | order by <col> [asc|desc] presentation pipe syntax, but eliminate all asymmetries, establish a formal Default Sort Order Contract, and support sorting in defaults.

4.1 The Canonical Default Sort Order Contract

When a query omits | order by, the engine applies the target's canonical default ordering:

Target Canonical Default Sort Order Rationale
:journal / :note order by date desc, createdAt desc, id desc Reverse-chronological journal expectation; deterministic tie-breaking.
:session order by completedAt desc, id desc Most recent workout sessions first. Lift the restriction: allow author overrides!
:block order by date desc, position asc Chronological parent note date, preserving authored block order within the note.
:effort order by label asc, slug asc Alphabetical lookup catalog.
:segment / :event order by date desc, timestamp desc Most recent performance rows first.
:catalog / :collection order by title asc Alphabetical browse view.
<agg>:<metric> by {dim} Points: ts asc; Series: value desc (if top-k) or label asc Chronological time points; highest volume series first.

4.2 Syntax Examples

// 1. Session query overriding the default completion-time sort:
:session{plane:segment} last 4w | order by duration desc | limit 10

// 2. Note query explicitly sorting by title:
:note{tags:benchmark} | order by title asc

// 3. Document-level default sort declaration:
defaults by {week} last 12w order by date desc

// 4. Aggregate query with top-K sorting:
sum:totalVolume{discipline:strength} by {effort} | order by value desc | limit 5

Advantages

  • Zero breaking changes to existing WQL queries.
  • Matches SQL and Datadog presentation conventions.
  • Fixes the :session limitation immediately.
  • Requires minimal changes to Lezer grammar (pipes are already split in JS).

Tradeoffs

  • Pipe | remains dual-purpose (presentation pipe vs pipeline stage).
  • Cannot put presentation pipes in the middle of a value pipeline.
  • Does not use bracketed {} syntax common to other WQL clauses.

5. Proposal B: First-Class Suffix Clause `sort by {}`

Promote sorting to a first-class bracketed suffix clause alongside by {dimension} and last <n>w. This cleanly separates relational query clauses from pipeline transformations.

5.1 Syntax Definition

// Grammar: Stage := Head Filters? GroupBy? Window? SortBy? DisplayUnit?
// SortBy: 'sort' 'by' '{' SortDimension (',' SortDimension)* '}'
// SortDimension: Word ('asc' | 'desc')?

:journal{effort:snatch} last 4w sort by {date desc}
:session{plane:load} sort by {duration desc, completedAt desc}
:effort{discipline:strength} sort by {label asc} limit 25
sum:totalVolume{} by {effort} sort by {value desc} limit 5

5.2 Separation of Concerns

Under Proposal B, the pipe token | is reserved exclusively for Unix-style value streams: 

// Clean pipeline without pipe overloading:
:journal{tags:benchmark} sort by {date desc} | :count{} | :bar{}

// Document defaults cleanly combine:
defaults by {week} last 12w sort by {date desc}

Advantages

  • Completely eliminates grammatical ambiguity between presentation pipes and pipeline stages.
  • Consistent syntax: by {dim} groups; sort by {dim dir} orders.
  • Can be extracted in JS suffix pass (wqlSuffix.ts) using existing brace-aware extraction.
  • Natural fit for WQL composer pills (e.g. [Sort: Date ↓]).

Tradeoffs

  • Requires deprecating legacy | order by or maintaining dual-path parser.
  • Changes established habit of SQL-style | order by col desc.

6. Proposal C: Two-Tier Relational Model (Groups + Rows)

Addresses the subtle problem that arises when both grouping (by {dim}) and sorting are present. In personal training logs, users frequently want to sort both the shelves (e.g., show the most active discipline first) and the cards on each shelf (e.g., show the newest workout first).

6.1 Two-Tier Sorting Syntax

Group Order by {discipline} order groups by {count desc} or by {discipline:desc}
Row Order | order by date desc or sort by {date desc}
Combined :journal{} by {discipline} order groups by {count desc} | order by date desc

How the Engine Evaluates Two-Tier Queries:

  1. Step 1 (Candidate Retrieval): Query storage with canonical default row order (date desc).
  2. Step 2 (Row Slicing / Sorting): Apply explicit row ordering (| order by date desc).
  3. Step 3 (Grouping): Partition rows into groups keyed by discipline.
  4. Step 4 (Group Ordering): Sort groups according to order groups by (e.g., group with highest count first).
  5. Step 5 (Pagination): Slice groups or flattened stream according to limit / offset.

Advantages

  • The only proposal that fully solves the UI shelf ordering vs item ordering conflict.
  • Allows "Top Disciplines" and "Leaderboard" views without complex subqueries.

Tradeoffs

  • Highest conceptual overhead.
  • Overkill for 90% of journal queries. Violates Lazy Senior Dev simplicity rule if adopted in Phase 1.

7. Storage Pushdown & Paging Spec

Regardless of which syntax is chosen, sorting must be pushed down to the storage tier to make limit and offset deterministic and high-performance.

7.1 The Domain Order Interface

In packages/wql/src/stores.ts, WqlDomainOrder currently supports limited fields. We formalize and extend it:

export type WqlDomainOrder = {
  field: 'date' | 'createdAt' | 'completedAt' | 'title' | 'id' | 'duration';
  direction: 'asc' | 'desc';
  nulls?: 'first' | 'last';
};

7.2 Corrected `domainPaging` Implementation

In packages/wql/src/QueryService.ts, domainPaging must resolve target canonical defaults before sending the query to the database:

function resolveDomainOrder(parsed: ParsedFindQuery): WqlDomainOrder[] {
  // 1. If explicit order by is authored, map it to domain fields
  if (parsed.pipes?.order?.length) {
    return parsed.pipes.order.map(o => ({
      field: mapColumnToDomainField(o.col),
      direction: o.dir,
    }));
  }

  // 2. Fall back to target's Canonical Default Sort Order
  switch (parsed.target) {
    case 'note':
    case 'journal':
      return [{ field: 'date', direction: 'desc' }, { field: 'id', direction: 'desc' }];
    case 'session':
      return [{ field: 'completedAt', direction: 'desc' }, { field: 'id', direction: 'desc' }];
    case 'effort':
      return [{ field: 'label', direction: 'asc' }];
    default:
      return [{ field: 'id', direction: 'asc' }];
  }
}

8. Lazy Senior Verdict & Phasing

Following the Senior Developer Ladder (Stdlib/native first, shortest diff, zero unrequested abstraction, deletion over addition):

Verdict: Adopt Proposal A (Standardized Pipes + Target Canonical Defaults) with Phased Upgrade Path

Do not invent new syntax like sort by {} today. WQL already has | order by col [asc|desc] in the parser and AST. The root problem is not the grammar—it is the absence of canonical defaults in QueryService, the hardcoded refusal in :session, and the broken id asc pushdown.
