WOD Wiki / implementation proposal / 16 October 2026

Effort and equipment,
in the note.

Keep the workout line readable. Make its effort and equipment linkable metrics. Edit both reference pages with the same Markdown experience as a journal note.

Proposed, not implemented This document reviews the current code, walks through the parser, and defines the page, seed, and editor changes together. It does not change the application.

Keep the existing Efforts L1 link. Add Equipment beside it. Use one note editor for each page, one source document per record, and one shared reference-resolution path for editor previews, seeds, execution, and saved output.

02 / Proposed experience

A reference page should still feel like a note

Keep the app header, L1 rail, contextual L2 links, page actions, and note outline. Put the title, compact properties, description, example workout, and related links in one reading column. Expand fields where they live instead of opening a detached form beside a second property table.

The extra L1 link is Equipment

Efforts already has its own zone. Add Equipment immediately after it, with the same active, hover, collapsed, keyboard, and mobile treatment. Use /equipment for the list and /equipment/:slug for detail. These equipment routes are proposed.

L2 on the list has New equipment, All equipment, and search. Detail has Up to Equipment, related efforts, and referenced workouts. Use the existing list and note-shell conventions; do not build a separate equipment dashboard.

Create, read, edit

  1. Choose New effort or New equipment. Open a draft in the normal page shell, with the same property editor and Markdown body as an existing note. No raw-text-only create screen.
  2. Create validates required fields and slug uniqueness before the first commit. On existing custom notes, show Saving, Saved, or Save failed. Keep invalid input and failed saves in the editor.
  3. Bundled notes show Make a copy to edit. A copy gets a new identity and navigates to its own page after the note and registry projection commit. Seed updates never overwrite the custom copy.
  4. At 375px, fields stack inside the document. No squeezed side companion. Raw source, headings, and metric actions remain keyboard-accessible.

Reuse JournalPageShell.tsx:51-94, FrontmatterCompanion.tsx:312-326, 344-498, MetricInlinePanel.tsx:38-96, 216-274, and useNotePageNav.ts. Move existing editing behavior inline; do not introduce another document model.

L1 destinations are defined in appNavTree.ts:268-303. Equipment entry routing already exists in entryActions.ts:74-76; migrate those entries to the dedicated equipment route while retaining generic note access to the same underlying note.

03 / Proposed source contract

Markdown is the editable source, not a generated report

Each definition is a Markdown note with explicit type, durable slug, label, and aliases. The effort note retains its existing nested baseAttributes. Equipment gets its own definition without effort-only fields. Registry entries are typed projections of these notes.

Effort definition

---
type: effort
id: effort-bundled-snatch
slug: snatch
label: Snatch
aliases:
  - dumbbell snatch
  - single-arm dumbbell snatch
baseAttributes:
  met: 6.0
  discipline: strength
  intensityTier: moderate
equipment:
  - dumbbell
registrySource: bundled
---
# Snatch

Movement guidance and variations.

```time
10 Dumbbell Snatch @15kg
```

Proposed additions are type: effort and equipment. MET is illustrative. Definition equipment describes this specific movement, not every movement in the discipline.

Equipment definition

---
type: equipment
id: equipment-bundled-dumbbell
slug: dumbbell
label: Dumbbell
aliases:
  - DB
  - dumbbells
registrySource: bundled
---
# Dumbbell

Setup, handling, links, and notes.

## Related efforts

[Snatch](/e/snatch)

Equipment fields follow effort identity conventions. Equipment identity is dumbbell; 15 kg belongs to a workout resistance metric, not this definition.

Frontmatter metrics on an ordinary workout note

---
title: Snatch practice
metrics.equipment:
  - dumbbell
metrics.rpe: 7
---
# Snatch practice

Keep the prose editable. It is not executable.

```time
10 Dumbbell Snatch @15kg
8 Snatch @12kg {"equipment":"kettlebell"}
```

Use flat dotted metrics.* keys, with block lists for multiple equipment references. That shape already round-trips through the generic frontmatter parser. Applying it to statements is new work. Do not introduce a nested metrics: map or rely on YAML inline lists until every editor and seed parser can preserve them.

metrics.effort: snatch may fill a missing effort on a quantity/load-only exercise line. It must not rename a line that already says Snatch, Run, or Rest. In a mixed workout, explicit line text is safer than a note-wide effort default.

Adding metrics while writing Markdown

Keep descriptive metadata separate from executable defaults. An effort definition's top-level equipment list describes that effort. Ordinary note equipment tags remain searchable tags. Only the explicit metrics.equipment namespace supplies note-wide workout defaults. This avoids changing the meaning of existing tagged notes.

  1. At the note properties, Add metric offers an effort lookup, equipment multi-select, or existing numeric metric. It writes metrics.effort, metrics.equipment, or another validated metrics.* key to frontmatter.
  2. Inside a time or log block, Add metric targets the focused statement. Selecting equipment writes an inline JSON object such as {"equipment":"dumbbell"}. Multiple items use a JSON string array, which requires new reference-value validation.
  3. Description, links, lists, images, and example blocks stay ordinary Markdown. [Dumbbell](/equipment/dumbbell) is a navigable link, not an instruction to add equipment to every nearby workout line.

Keep the existing syntax. JSON object keys must be quoted. The current parser silently ignores malformed {equipment: dumbbell}. Brackets such as [equipment:dumbbell] are actions and can trigger climbing interpretation. Neither is an equipment annotation syntax. Add a diagnostic for invalid reference objects rather than inventing another delimiter.

Sources: frontmatter.ts:43-56, 118-143; syntax-parser.ts:312-333; semantic-classifier.ts:124-146; sectionParser.ts:8-12, 75-107. The inspected note section parser recognizes time and log fences. Older docs mentioning wod do not define the current editor contract.

04 / Parser walkthrough

The line label can include the equipment name

10 Dumbbell Snatch @15kg
  1. Current parseDocumentSections identifies the fenced time or log block. Only its script content goes to the workout parser. Frontmatter and prose are separate note sections.
  2. Current createParser().read calls parseScript. Lezer reads the line; syntax-parser.ts creates typed syntax facts and indentation relationships.
  3. Current classifyStatements creates RepMetric(10) and an EffortMetric for the words. Adjacent effort fragments merge into Dumbbell Snatch. Unit dialect handling yields a resistance amount of 15 kg. Source text and offsets remain available.
  4. Current Registry resolution is separate from syntax parsing. EffortResolver tries slug, alias, then fuzzy match with a synthetic fallback. applyEffortEnrichment resolves a compiled block's label into private effort-data; analytics also resolves output statements.
  5. Proposed Resolve references on statement metrics before preview, containment indexing, and compilation. An explicit effort reference wins. Otherwise, resolve an unambiguous equipment-prefix alias and the remaining movement before trying the entire phrase as one effort. For this line, effort is snatch and equipment is dumbbell, not effort dumbbell-snatch.
  6. Proposed Match the longest exact equipment-prefix alias whose remaining phrase resolves exactly to an effort. Dumbbell + Snatch yields separate equipment and effort metrics when both definitions exist and the interpretation is unique. Keep Dumbbell Snatch as the authored label, while the effort chip shows Snatch. Never globally remove equipment words.
  7. Proposed Attach canonical reference data to the metrics, then let the editor, compiler, runtime output, and index readers consume it. Do not make each consumer re-parse display labels. Retain the existing effort-data calculation payload for MET and analytics.
A validated equipment-and-movement split takes precedence over a whole-phrase effort match. Words are not equipment merely because they precede a movement: Turkish Get-Up stays intact without a valid equipment-prefix match. Row can be an effort or an equipment alias. Unknown or ambiguous text stays editable and shows an unresolved diagnostic; never silently choose a different movement.

Keep fuzzy results available as estimated effort suggestions or the existing analytics fallback. Do not use fuzzy matches to create durable equipment references or seed containment rows. Accepting a suggestion writes an explicit canonical reference.

One precedence rule, used everywhere

For equipment, use explicit line JSON first, an unambiguous equipment name in the line second, explicit note metrics.equipment defaults third, and the resolved effort definition's equipment last. For effort, an explicit line reference wins over line phrase resolution; note metrics.effort only fills an otherwise missing exercise effort. Apply defaults only to exercise statements, not headings, timers that only group children, or rest.

If explicit equipment contradicts a specific movement definition, retain the authored source and show the conflict before execution. Do not silently rewrite Dumbbell Snatch to Kettlebell Snatch. Let the user choose a compatible effort or remove the conflicting override.

An explicitly authored but unknown reference is not an absent value. Keep it in the draft, show an unknown-reference message with Create page or Select existing, and do not fall back to a different inferred reference. Only validated references enter resolved metrics and durable indexes.

Reuse the current metric origin and ownership model. Explicit script metrics remain parser-origin; note defaults and inferred references carry source metadata and lower precedence during resolution. User-plan overrides and collected runtime values retain their existing ownership. Do not add equipment inference by pretending it was a user measurement.

06 / Proposed seeds and persistence

Ship the pages, not just the navigation link

  1. Add a recognized markdown/equipment/<slug>.md family and an equipment reserved chunk, parallel to efforts. Keep the current notes chunk kind and full Markdown source. Do not create a second JSON-only catalog of labels.
  2. Validate type, slug, label, alias collisions, and equipment references in effort definitions. Missing referenced definitions are build/import diagnostics. Custom catalogs may reference already installed dependencies, but unknown references must remain visibly unresolved rather than resolve by substring.
  3. Import equipment notes and typed equipment projections atomically with source ownership and checkpoints. Project each definition's owning note ID so routes open the real source note. Preserve seedNoteId(path); do not create another synthetic note merely to edit a seeded definition.
  4. Use the same exact reference resolver for static build and local note-save projections. Current block-effort links must use explicit effort identity where present; equipment usage links must use resolved equipment metrics. Build related-page lists from these references, never by searching rendered labels.
  5. Seed refresh can replace or remove only seed-owned definitions and their derived links. Preserve custom copies and local notes. Keep source ownership when catalogs overlap; removing one source must not erase another source's definition or a user's copy. A slug collision needs a visible policy, not import-order overwrite.
  6. Export and re-import must preserve Markdown, nested effort attributes, equipment links, metric defaults, and note/block identity rules. If the wire format adds equipment projections, bump the seed schema and regenerate artifacts; do not silently reinterpret schema 8 rows.

Canonical source is the saved note. The effort/equipment record is its lookup projection. A save must not report success while the note and projection disagree. The current effort hook saves the note and then upserts the registry in separate awaits; use a single storage transaction for the cutover and refresh the in-memory registry after commit.

Current seed contract: contract.ts:4-14, 47-77. Transaction and ownership: runtime.ts:66-102, 158-177, 211-231. Effort maps and containment: compiler.ts:349-372, 459-492. Current local two-step save: useEffortContent.ts:134-145.

Do not copy the old corpus paths or effort-format parser again. This checkout already has separate app and engine effort parsers. Put the definition-format parsing and validation in the existing headless language package, and migrate both callers. Keep note section detection consistent with explicit type: equipment; the current heuristic can misclassify equipment metadata as effort.

Acceptance walkthrough

  1. Start with a fresh local store. Import a small real catalog containing Dumbbell and Snatch. Both pages open through their lists and direct URLs. Equipment appears in L1. The effort's equipment link opens Dumbbell.
  2. Create an equipment note, add aliases and a Markdown description, then reload. Create an effort in the same layout and link the equipment. Change one property and prove nested MET, hints, derivation, unknown fields, and prose were not lost. One undo restores the source change.
  3. In an ordinary note, use the example line and explicit JSON equipment. Verify effort/equipment chips and page links, frontmatter defaults, line precedence, a conflicting override, an unknown slug, and colliding aliases. Test both time and log.
  4. Run the changed line and save a session. Reload its output and verify the canonical effort/equipment references, authored text, origins, and unchanged load. Compare the same source's CLI/seed projection with the editor result.
  5. Edit a bundled page through Make a copy to edit. Refresh and remove its seed source. The original follows source ownership; the custom copy and its Markdown remain. Simulate a persistence failure and verify the draft is retained and success is not reported.
  6. At 375×812 and desktop width, reach both L1 entries, create/edit fields, raw source, metric actions, and backlinks using keyboard and pointer. No second metadata editor, clipped picker, or horizontal page overflow.

Leave focused consumer-behavior coverage for reference resolution, lossless property edits, ownership transitions, and the end-to-end note workflow. Do not test copied labels or implementation wiring. This document's annotation check is separate from those future application acceptance checks.

Deliberately not included

Equipment taxonomy and new query-language nouns are not prerequisites for the requested pages. Add them only when a concrete workflow needs them; equipment references, page links, and usage lists are in scope now.
