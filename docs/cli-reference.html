wod CLI Reference

wod v0.6.0 provides the headless Whiteboard Language & WQL pipeline (parse/run/query), a self-hosted HTTP API + website (server, also serve), and a browser-only playground (playground). The installed package includes both websites and the API; hosting requires Bun but no checkout or runtime build. Databases: SQLite, PostgreSQL, or Turso/libSQL, configured via flags, environment variables, or a .env file. Source of truth: packages/engine/src/cli/runner.ts + packages/engine/src/cli/config.ts; HTTP handler: packages/engine/src/server/app.ts.

Commands

CommandArgumentsWhat it does
wod parse <file | -> Parses a Whiteboard Script from a file (or - for stdin) and persists it as an authored note in the configured database (any backend): whole source, a saved revision, and a sparse block index. Frontmatter tags (general + typed equipment/quality/…) are materialized into the tag graph. Markdown carrying a wod-note-id frontmatter stamp re-imports into that same note.
wod run <file | -> Executes the script's state machine and records a session plus event and summary rows in the database. Bare (non-markdown) input is wrapped as an authored note first.
wod query '<wql>' Evaluates a WQL query string against the database, or against an explicit dataset chosen with --corpus / --stdin-log / --stdin-facts. Emits a QueryResult / RowsQueryResult IR payload.
wod download <note|session|effort|equipment> <id> Exports database content to files for round-tripping: note writes authored markdown (with the identity stamp that allows re-import), session writes generated metrics as CSV (one row per metric event), effort writes a registry row as corpus-style markdown, equipment writes every equipment tag as a one-column CSV (no id needed).
wod import <note|session|effort|equipment> <file> Counterpart to download: re-imports note markdown (same as parse with stamped identity), imports a session + events from downloaded CSV (the exact saved block revision must already exist), upserts an effort registry row from corpus-style markdown, or creates/upgrades equipment tags from a one-label-per-row CSV.
wod build [dir] Compiles a seed corpus: validates every .md under <dir>/markdown (parity gate + dashboard format gate), then writes manifest.json, content-hashed chunks/, and report.html to <dir>/dist. Version stamps derive from <dir>'s git history, so a full checkout is required.
wod seed — Imports compiled seed directories (manifest + chunks) into the database. Defaults to the bundled core + community artifacts under apps/playground/public/seed; replaces the defaults when --source is given.
wod reset — Deletes the local SQLite database file entirely (a fresh one is created on demand by parse/run/seed). Remote backends are refused — clear PostgreSQL/Turso databases through their provider.
wod init — Initializes the configured database, idempotently and preserving existing records: creates the SQLite file + schema; creates the PostgreSQL database + schema when the connecting role is authorized (otherwise targets an existing/provisioned one); installs the schema in the provisioned Turso database (the hosted database must already exist). Run once before server.
wod server / wod serve [options] Serves the packaged app over HTTP with Bun: a same-origin API over the configured database plus the static website. Refuses a missing/uninitialized database with wod init guidance. No checkout, runtime build, or authentication.
wod playground [options] Serves the packaged IndexedDB-backed playground with Bun. No backend (every /api request answers 404), and the configured database is never touched. No checkout or runtime build.
wod help
wod version		 — Subcommand equivalents of --help and --version.

--dist<dir>Serves this prebuilt frontend directory instead of the packaged server app ($PLAYGROUND_DIST), resolved relative to the working directory. A missing directory is an error; no build runs at startup.

Also accepts the shared database flags (Database options). Install with bun add --global @bitcobblers/wod-wiki-engine, then run wod init --db ./data/wodwiki.db and wod server --db ./data/wodwiki.db. Options: playground

FlagValueWhat it does
--host<host>Bind address (default 127.0.0.1; $HOST).
--port<port>TCP port (default 3000; $PORT).
--dist<dir>Serves this prebuilt frontend directory instead of the packaged playground ($PLAYGROUND_DIST), resolved relative to the working directory. A missing directory is an error; no build runs at startup.

Serves the packaged IndexedDB-backed build with Bun; no backend is started. No checkout or frontend build tools are needed. Database flags are accepted but ignored; the configured database is never opened.

Database options: shared

Applies to init, parse, run, query (default input only), download, import, seed, server/serve, and reset (local files only); playground ignores it. Precedence: flags > process environment > .env file. --db always selects local SQLite, even when the environment names a remote backend. Conflicting explicit selectors (e.g. --db with --turso-url, or --database-url with --postgres-* flags) fail, as does ambiguous environment configuration (set DB_DRIVER to choose). Credentials are never printed.

FlagValueWhat it does
--db<path>Local SQLite database file (default $WOD_WIKI_DB, then $SQLITE_PATH, then ./wodwiki.db); created on demand by init/parse/run/seed.
--db-driversqlite|postgres|tursoBackend driver ($DB_DRIVER; default sqlite).
--database-url<url>Driver-scoped connection URL ($DATABASE_URL): postgres:///postgresql:// for PostgreSQL; libsql://, https://, http://, wss:// or file:// for the libSQL/Turso protocol (a remote libSQL URL normalizes to the Turso backend). Never combined with a competing selector.
--postgres-host<host>PostgreSQL host ($POSTGRES_HOST; default 127.0.0.1 in per-property form).
--postgres-port<port>PostgreSQL port ($POSTGRES_PORT; default 5432).
--postgres-user<user>PostgreSQL user ($POSTGRES_USER).
--postgres-password<pw>PostgreSQL password ($POSTGRES_PASSWORD; never printed).
--postgres-database<db>PostgreSQL database name ($POSTGRES_DATABASE); required for per-property PostgreSQL configuration.
--postgres-ssl<mode>PostgreSQL SSL ($POSTGRES_SSL): requires true/false or disable|prefer|require|verify-ca|verify-full (default prefer).
--turso-url<url>Turso/libSQL database URL ($TURSO_DATABASE_URL, then $DATABASE_URL): libsql://, https://, http:// or wss://. The hosted database must already exist (provisioned on Turso); init only installs the schema.
--turso-auth-token<token>Turso authentication token ($TURSO_AUTH_TOKEN, then $LIBSQL_AUTH_TOKEN; never printed).
--env-file<path>Loads environment variables from this file; explicit use is mandatory — a missing file is an error. Without it: ./.env when present, otherwise the nearest ancestor (workspace-root) .env.

Conventions

ConventionDetail
- as inputparse and run read the script from stdin when the input argument is -.
- as output-o - (or --output=-) writes the payload/export to stdout instead of a file.
Flags with =Both --flag value and --flag=value spellings work for the database/hosting flags (--db, --db-driver, --database-url, --postgres-*, --turso-*, --env-file, --host, --port, --dist) and for --output/--out, --format, --pack, --source, --template, --dir. --corpus, --sport, and --unit accept only the space form; --debug is a bare flag — a custom file name requires --debug=<name>. --out is an alias of --output.
DatabaseOne shared database configuration across init/parse/run/query/download/import/seed/server/serve/reset, resolved as flags → process env → .env (see Database options). SQLite default; --db always pins SQLite over a remote env backend; playground never touches the database; reset only removes a local SQLite file.
Round-trippingdownload/import pairs (note ↔ md, session ↔ csv, effort ↔ md, equipment ↔ csv) are the supported export/import paths; note markdown carries a wod-note-id frontmatter stamp so re-import updates the same note.
