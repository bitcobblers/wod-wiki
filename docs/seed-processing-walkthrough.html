Seed processing, end to end

How Markdown becomes a published seed, how playground and Storybook build their own core, how the browser downloads and commits records, and where the current screens repeat work that belongs in one place.

This guide covers the code after the app-owned core consolidation and the granular membership fixes. It calls out proposals separately from behavior that exists today.

1. The short version 2. Shared build pipeline 3. Playground and Storybook 4. Artifacts and versions 5. Runtime downloads and storage 6. Screens and interactions 7. Duplication and simplification 8. A smaller target shape 9. File map and gotchas

1. The short version

Every seed starts as a Git repository of Markdown. One compiler turns that corpus into static JSON. The app fetches that JSON over HTTP, compares versions and per-record commits, then writes changed records and their projections into local storage. Users never need a seed server with application logic. GitHub Pages, the app origin, or any HTTPS static host can publish the artifacts.

Consumesync worker, IndexedDB, screens

Already shared

generateSeed() builds core and community seeds. HttpSeedSource reads all of them. applySeedChunk() is the shared atomic commit operation. Precedence and user-ownership rules apply across sources.

Still duplicated

Contract files have copies, one validator has drifted, boot policy lives in three drivers, a manifest is fetched twice per import, and several screens format progress and handle subscriptions independently.

Good constraint. Static hosting and local-first storage are not sources of duplication. They are the reason the system works offline and why community publishers need no backend.

Primary entry points: packages/tools/src/seedbuild/compiler.ts, scripts/sync-seed.ts, apps/playground/src/services/seed/seedSync.ts, packages/engine/src/seed/runtime.ts.

2. The shared build pipeline

The public wod build command and the repo-internal scripts/sync-seed.ts both call generateSeed(). The compiler is Node-only because it reads files and Git history. It is not part of the browser bundle.

  1. Resolve the repository. The compiler reads corpusRoot, markdownDir, outDir, and package.json. resolveGitVersion() collects the commit count, describe label, HEAD SHA, and dirty flag. An optional --scaffold pass creates stubs for uncatalogued efforts.
  2. Scan and partition. A sorted recursive scan finds Markdown. chunkIdFor() maps canvas, dashboards, efforts, and equipment to reserved chunks. Collections and feeds become collection.<slug> and feed.<slug>. An unknown corpus directory fails the parity gate instead of silently bypassing publication.
  3. Compile occurrences and projections. compileSeedRow() keeps exact Markdown and reconciles fenced blocks. Other passes create the block index, effort links, and equipment links. Dates prefer frontmatter, then feed paths, then Git history. Only references resolved by the shared catalog enter durable links.
  4. Validate. Every workout block must parse. Dashboard notes need valid frontmatter, at least three known widgets, parseable aggregate WQL, and declared tokens. The manifest is shape-checked before publication. Row-level projection validation currently happens on import, not during this build gate.
  5. Write immutable artifacts. The compiler wipes outDir after the gates, then writes per-record JSON, full chunk JSON, notebook indexes, the manifest, and report.html. Reading the previous manifest for a change report must happen before that wipe.

External wod-wiki-seed-* repositories

The eight locally inspected content repos use the same shape: markdown/, a package script that runs wod build, and two GitHub workflows. Push-to-main builds with full Git history and deploys dist/ to Pages. Pull requests run the same build, upload the report, and update a sticky summary comment. Their layouts differ by theme, not by compiler.

What happened to the old Core Registry?

The registry entry and its default URL are gone. Existing installations migrate seed:seed-core memberships into seed:core. Migration preserves seedVersion so offline content remains usable, clears builtAt to force revalidation, then blanks the old checkpoint. Storybook runs the same migration before its imported probe.

The separate wod-wiki-seed-core repository still publishes artifacts even though the apps no longer consume them. Its efforts and equipment have drifted from the main corpus. That repository now needs an explicit retirement or derived-mirror decision.

Build orchestration: scripts/sync-seed.ts. Stamps: both app Vite configs. Migration: adoptLegacyCoreRegistryCheckpoint() in seedSync.ts and Storybook's DatabaseContext.tsx.

4. Artifacts and versions

A published seed is a directory, not one payload. The manifest is the small discovery document. Full chunks remain available, while record references let current clients download only changed files.

A local SeedMetaRecord is separate again. It records the applied source version, chunk hashes, full note membership, precedence tier, and an optional cross-tab claim. Confusing these values leads to bad sync decisions.

5. Runtime downloads and storage

Fresh browser

  1. Open storage. BootGate waits for IndexedDB or the API data plane before rendering the app.
  2. Start bootstrap. GlobalState initializes broadcasts, profile identity, and startSeedBootstrap(). Legacy checkpoints and subscriptions migrate before the core probe.
  3. Fetch core. With no usable checkpoint, the readiness gate enters preparing. A worker claims the source, fetches its manifest, and chooses import.
  4. Plan and download. SeedImporter puts canvas first. It compares local record commits with manifest refs and downloads only missing or changed record JSON. Full chunk download remains the fallback when no record refs exist.
  5. Commit and ungate. applySeedChunk() writes rows, projections, history, membership, and checkpoint in one transaction. Canvas commit triggers first-paint hydration and the home route becomes available.
  6. Finish in the background. Other chunks and subscribed update checks continue. Broadcasts and registry refreshes keep other tabs and consumers in sync.

Returning browser

A core checkpoint lets the app render immediately. Background sync probes manifests. If the stored core matches the build-stamped version, it can skip even that fetch. Auto-sync sources apply updates; other subscribed sources produce update-pending entries without downloading content. Returning outcomes do not re-gate the UI.

Manual actions

  • Subscribe or import: syncSeedSource() fetches and imports, then subscribes unless Import Once explicitly declines that state.
  • Sync now: Settings uses a forced sync; background update checks remain non-forced.
  • Unsubscribe: exact source-owned rows and the checkpoint are deleted in one transaction. User-owned rows and other checkpoints survive.
  • Delete source: unsubscribe, then unregister a custom source or hide a built-in one.
  • Custom URL: validate an HTTPS seed directory, probe its manifest, then use the same import pipeline as a built-in source.

Atomic work versus background work

Atomic

Claim writes use compare-and-swap. Each chunk commits rows, projections, membership, and checkpoint in one transaction. Source removal is also one transaction. Full manifest membership, not the downloaded subset, decides which notes vanished.

Incremental and background

The chunk sequence is resumable rather than atomic. A crash leaves committed chunks for the next run. Cache hydration, content broadcasts, check timestamps, and update notifications happen around those commits.

With real IndexedDB, the worker does network, parsing, and writes off the main thread. API storage uses the direct main-thread path. If the worker cannot start, the driver retries through the direct path using the same claims and checkpoints.

Runtime chain: seedReadiness.ts → seedSync.ts → seedSyncCore.ts → SeedImporter.ts → packages/engine/src/seed/runtime.ts. Content hydration continues through seedContent.ts and canvasRoutes.ts.

7. Duplication and simplification

The remaining duplication is mostly copy-keeping and inconsistent policy. A rewrite would make it worse. These changes keep the current compiler, static hosts, worker, and storage model intact.

8. A smaller target shape

The target is fewer owners, not more layers. The existing seams are already adequate for most of the cleanup.

One contractschema, manifest, validator, frontmatter subset
→
One build plangenerateSeed for every publisher
→
One sync planmanifest once, boot policy once, targeted imports
→
One presentation policyprogress, outcomes, hydration, removal

Build ownership

Tools performs Node I/O and Git archaeology. Engine or core owns the pure contract and strict validation. Every publisher runs the same row and manifest gates before writing artifacts.

Runtime ownership

The sync core receives one manifest and one checkpoint, then returns a plan. The importer executes it. Engine owns both chunk application and source removal. App code adapts that result to storage and UI state.

Screen ownership

Screens request actions such as subscribe, toggle notebook, or retry. They do not decide force, duplicate migration, or invent outcome text. A shared formatter and global notifier explain what happened.

App ownership

Playground and Storybook keep their static output and readiness adapters. A pure boot plan decides what to sync; each app decides how to display progress and when its own content is ready.

Best first slice. Single-source the contract and validator, then pass the manifest through. Both are small, measurable changes with existing tests. The boot and screen policy cleanup can follow without changing artifact formats.

Non-obvious behavior worth remembering

  • Community sources use embeddedVersion: 0 so app releases do not control when Pages updates are noticed.
  • Granular downloads contain changed rows only. Deletion must use the manifest's complete membership, or unchanged siblings disappear.
  • A source can report imported with an empty download plan when metadata changed. It describes the attempted apply, not a bandwidth estimate.
  • Core migration preserves seedVersion and clears builtAt. That forces revalidation without making a returning user behave like a fresh install.
  • User deletion tombstones suppress re-import. User-edited rows outrank seed rows and are never overwritten.
  • getSeedContent() currently scans all notes when rebuilding its corpus map. Treat indexing as a measured performance task, not a prerequisite for the policy cleanup.
  • Older catalog architecture documents describe retired topology. Check code before using them as current-state references.

Evidence limits

Build inspection covered eight local wod-wiki-seed-* repositories. The other seven registered YouTube, example, and Reddit publishers were not inspected. The walkthrough covers their runtime registration, not unverified CI details. Recommendations are analysis only; no implementation is implied.
