Architecture & Strategy Whiteboard Review

Catalogs & Distributed Seed Data Architecture

A comprehensive architectural guide for decentralized workout catalogs: compiling custom distribution repositories with the wod CLI, local-first subscription lifecycles, in-situ catalog settings on /catalogs, one-click subscription links, and publication mechanics.

1. Architectural Paradigm: The Distributed Seed Model

WOD Wiki follows a strict local-first data plane. Workouts, notes, logs, and metrics written by athletes are stored in their own local database (browser IndexedDB or local SQLite). However, athletes and coaches require access to canonical benchmarks (e.g. The Girls, Hero WODs), training programs (e.g. Dan John 40-Day, box programming), movement definitions, and analytics dashboards.

Rather than centralizing all training content in a proprietary SaaS database, WOD Wiki implements a content-addressed, distributed seed model. Anyone can maintain and publish a catalog repository as plain Markdown files. Any WOD Wiki instance can subscribe to one or more catalog repositories and pull deterministic, version-stamped chunks directly into local storage.

Architectural Principle Implementation in WOD Wiki Benefit
Content-Addressed Chunks Each chunk file name includes a SHA-256 fingerprint (e.g. collection.crossfit-girls.a1b2c3d4.json). Immutable caching: browsers and CDNs cache chunks permanently with max-age=31536000, immutable. Only changed chunks are downloaded during updates.
Seed Origin Isolation Imported rows carry seedOrigin: 'seed' and seedChunkId. User-authored notes are stamped with seedOrigin: 'user'. Safety guarantee: updating or deleting a catalog never touches or overwrites athlete journal notes or custom user workouts.
Atomic IndexedDB Transactions IndexedDBSeedImportStorage.applyChunk executes the note and block index mutations in one transaction per chunk. No partial corruption: if network drops mid-sync, the database retains the previous valid checkpoint.
Pre-Compiled Projections The compiler pre-computes the Lezer CST, block index, and block efforts on the build machine. Zero client parsing overhead: client devices ingest ready-to-query index rows directly into IndexedDB without burning CPU/battery.

Any Git repository containing workout Markdown files can become a WOD Wiki catalog distribution. The @bitcobblers/wod-wiki-tools CLI provides the standard compiler.

The wod build Command

The compiler evaluates every file in the corpus against strict grammar and format rules, derives block indexes, links referenced effort definitions, and emits static artifacts:

# Install the tools globally
bun add --global @bitcobblers/wod-wiki-tools
# (or npm install --global @bitcobblers/wod-wiki-tools)

# Run the build from the repository root
wod build . --output dist --scaffold
Option Description
[dir] Corpus root containing the markdown/ directory (defaults to current working directory .).
-o, --output <dir> Output directory for compiled artifacts (defaults to <corpusRoot>/dist).
--scaffold Automatically scans workout bodies for effort names and generates markdown/efforts/discovered/*.md frontmatter stubs for missing movements.
--template <file> Injects an optional intake template chunk (used by host applications for scratchpads).

Automated Validation Gates

  • Lezer CST Parse Gate: Every Whiteboard script block is validated through createParser(). Syntax errors produce precise file:line diagnostics and halt the build.
  • Dashboard Constraint Gate: Files in markdown/dashboards/ must contain valid frontmatter, a declared title, ≥ 3 valid widgets, and declared $token parameters.
  • Effort Slug Extraction: Workout lines are cross-referenced against the effort registry to ensure movement containment queries (e.g. :session{effort:thruster}) resolve.
  • Git Version Derivation: Monotonic build numbers and commit hashes are computed via git rev-list --count HEAD and git rev-parse --short HEAD.

Automated Publishing GitHub Actions Workflow

Below is the recommended workflow file for any catalog repository (.github/workflows/publish-catalog.yml):

name: Publish Catalog

on:
  push:
    branches: ["main"]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: true

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0 # Full history required for git version stamping

      - name: Install Bun
        uses: oven-sh/setup-bun@v2
        with:
          bun-version: latest

      - name: Install WOD Wiki Tools
        run: bun add --global @bitcobblers/wod-wiki-tools

      - name: Compile Catalog
        run: wod build . --output dist

      - name: Setup Pages
        uses: actions/configure-pages@v4

      - name: Upload Pages Artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: dist

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4

Current Sync, Import, and Deletion Mechanics

1. Sync & Import Lifecycle (seedSync.ts)

  • Manifest Check: Fetches manifest.json from the origin URL. Verifies schema === SEED_SCHEMA.
  • Version Gate: If remote version > stored.version or force === true, imports chunks.
  • Streaming Progress: Fires events across checking → fetching → applying → committed → finalizing.
  • Reactive Broadcast: Transmits on BroadcastChannel('wodwiki-seed') so open tabs immediately see new collections without a page refresh.

2. Collection Deletion Lifecycle (removePackageFromLibrary)

  • Target Filter: Queries storageService.getAllNotes() and identifies notes matching note.seedOrigin === 'seed' and the package's chunkId / catalog slug.
  • Cascade Delete: Invokes storageService.deleteNote(id) for each note, cleaning block revisions and block index rows.
  • Checkpoint Purge: Removes the seedMetaKey(packageId) row in IndexedDB meta table.
  • Unsubscribe: Clears the subscription flag in localStorage['wodwiki.seedSubscriptions'].

Current Gap: The deletion function removePackageFromLibrary() is currently exposed in TourJumpSection.tsx and OfferingTiers.tsx on the home tour, but is absent from the SyncSection.tsx cards and the main /catalogs page. In SyncSection.tsx, clicking "Remove" only unregisters the custom HTTP source from localStorage; it leaves the previously imported notes in the vault.

4. In-Situ Catalog Settings on the /catalogs Screen

Currently, /catalogs is rendered via QueriableStreamView with CATALOGS_STREAM_PROFILE (default WQL: :catalog{} by {tag}). It shows a clean stream of workout cards grouped by category or tag. However, there is a disconnect: athletes browsing catalogs have no way to manage, inspect, or add sources directly where they view them.

Proposed Design: Direct Catalog Management Drawer / Modal

We propose adding a direct "Manage Catalogs" action in the /catalogs header toolbar that opens an in-situ slide-over sheet or modal. Athletes can view installed catalogs, check for remote updates, install new collections, or delete existing ones without context-switching to /settings/sync.

5. One-Click Subscription Links (Direct Deep-Link Intake)

To enable frictionless decentralized sharing, gym owners, coaches, and community creators need the ability to share a single URL that prompts athletes to subscribe to their catalog. For example:

https://wod.wiki/catalogs?subscribe=https%3A%2F%2Fcrossfit-invictus.github.io%2Fdaily-wods%2F&label=Invictus+Athlete

Subscription Link Intake Lifecycle

1
URL Parameter Interception (/catalogs?subscribe=...)

When the application mounts or navigates to /catalogs, a router effect inspects the query string for subscribe (and optional label).

2
Remote Manifest Probing & Safety Verification

Before writing to disk or asking the user, the app performs a lightweight background fetch(subscribeUrl + 'manifest.json').

  • Verifies HTTPS protocol.
  • Checks that manifest.schema === 8 (compatible with current client parser).
  • Reads chunk count, total workouts, and build timestamp.
3
Confirmation Dialog (The "Import Offer")

The application displays an explicit intake modal presenting the catalog metadata and origin host with three distinct user choices.

Clean URL Sanitization

Upon user acceptance or dismissal, the app invokes window.history.replaceState(null, '', location.pathname). This cleans the query parameters so reloads or browser back-forward actions do not prompt the user again.

6. How Catalogs Are Published & What Is Generated

When a catalog publisher runs wod build, it generates an optimized static bundle consisting of three core deliverables.

1. The Manifest (manifest.json)

The manifest serves as the discovery index. Clients download this small JSON file first to determine if updates are available before fetching any chunks.

3. The Visual Audit Report (report.html)

Generated alongside the manifest by packages/tools/src/seedbuild/report.ts, report.html is a human-readable diagnostic dashboard showing:

  • Total files compiled, total byte payload, and individual chunk sizes.
  • Compilation timings across the 5 build passes (scan, block index, parse gate, block efforts, write).
  • Parity verification table ensuring every Markdown file belongs to a recognized corpus segment.
