Guide Stage Targeting: Beyond the Editor

Whiteboard · wod-wiki · 2026-10-19 · Question: can a guide stage target an image or other rendered markdown/HTML (a specific component) instead of only the timer results or the editor?

Short answer. Today a guide stage’s highlight ring can only frame the editor panel, a line range inside it, or one of 15 hardcoded tour surfaces. But the caption column already renders arbitrary markdown (images, tables, query widgets), and a generic data-effect-target attribute already lets stages animate any markdown-rendered element. So: arbitrary content renders and can be stage-driven today; what’s missing is the ring pointing at it, a non-editor stage pane, and dynamic conditional steps. Proposals below.

1. How the mechanism works today

Guide pages are canvas markdown files (markdown/canvas/guide/*.md, eight routed chapters). A page-level ```scroll fenced block declares a scroll runway; each stage in it is the markdown-DSL equivalent of the home tour’s TourStage.

A stage is a flat YAML-ish item. Real example, from markdown/canvas/home/README.md:

```scroll
runway: 720vh
screen: editor
stages:
  - id: timer-intro
    range: [0, 0.166]
    screen: timer
    caption: "Click Run to start the Timer. ..."
    ring:
      key: editor.runButton
      tag: Run Button
  - id: wql-idea
    range: [0.5, 0.666]
    caption: "Query what you just did. ..."
    ring:
      tag: "WQL elements"
```

What each stage field controls, and what it can point at:

Stage fieldParsed intoWhat it can target today
source: ScrollStage.source → editor document swap Only the editor pane (resolveSource on wods/examples/**).
caption: ScrollStage.caption → ScrollCaption → CanvasProse Anything markdown renders: prose, tables, images (<figure>), ```query widgets, code fences. Full component surface already.
ring: { key?, tag?, lines? } | true Scroll runways: the editor window only, or a 1-based inclusive lines: range (ScrollRing.tsx hardcodes “container’s first child = EditorWindow”). key/tag are parsed but unused here. Home tour: one of 15 hardcoded RingTargetKey strings registered via React context (TourRing.tsx).
screen: 'editor' | 'timer' | 'analytics' | 'result' The ScrollSpec comment says “Only ‘editor’ supported in v1”. The tour screens are the four app surfaces — no image/doc/web pane.
effects: ScrollEffect[] Any descendant of the runway root carrying data-effect-target="<id>", queried with querySelectorAll and driven through opacity/translateY windows. The generic-targeting pattern already exists — for parallax only.
toast: / quest: transient message / quest fire Chrome only; no targeting.

So the targeting model has two halves:

  • TodayThe pane is always the app surface (editor/timer/analytics/result). Its sub-elements are addressable two ways: doc lines for the editor, or the tour’s closed RingTargetKey registry (screens register wrapper elements under those keys through RingTargetsContext).
  • TodayThe caption is free markdown. data-effect-target proves stages can already reach into arbitrary rendered markdown DOM — the lookup is a plain selector scoped to the runway root, no registry.

2. What this means for the question

Already possible without code changes: a guide step whose “target” is an image, table, or embedded component in the caption column, brought to life per-stage with effects: parallax (fade/slide as the stage activates). The content is markdown; the addressing is a data attribute; reproduction is copy-paste.
Not possible today: the focus ring hugging that image/component (the “look here” affordance), a stage whose main pane is an image or rendered markdown doc instead of the editor, or steps that appear conditionally (e.g. “only if you use notebook sync”).

3. Proposal — markdown-reproducible definitions

Five incremental ideas. A and B are small diffs on existing seams; C–E follow the same DSL shape.

Idea A Generic ring target via data attribute

Extend the ring contract exactly like data-effect-target already does for effects: a stage names a target id; any markdown-rendered element carrying data-guide-target="<id>" inside the caption (or pane) gets the ring. Resolution order: lines > target > whole editor (today’s default).

### A guide page can be pure prose + components, no editor at all:

```scroll
runway: 400vh
screen: doc
stages:
  - id: open-settings
    range: [0, 0.34]
    caption: "Open Settings → Sync and copy your seed URL."
    ring:
      target: settings-sync     <- new: matches data-guide-target below
  - id: paste-seed
    range: [0.34, 0.67]
    caption: "Paste the seed URL into your notebook's sync field."
    ring:
      target: seed-url
  - id: verify
    range: [0.67, 1.0]
    caption: "Save; the badge turns green when the first sync lands."
```

<!-- anywhere in the page's ordinary markdown -->
<figure data-guide-target="settings-sync">
  <img src="assets/guide/settings-sync.png" alt="Settings sync tab" />
</figure>

<p data-guide-target="seed-url"><code>https://wod.example/seed/a1b2…</code></p>

Code touch: ScrollRing.tsx gains one resolution branch (query [data-guide-target] within the runway root, fall back to the EditorWindow measurement), plus one parsed key in parseScrollStages. The tour’s closed RingTargetKey registry stays untouched.

Idea B screen: doc — a markdown pane instead of the editor

The stage pane renders CanvasProse over inline markdown or a referenced .md file, reusing the exact renderer captions already use. The ring then targets inside the pane via Idea A.

```scroll
runway: 300vh
screen: doc
stages:
  - id: backup-intro
    range: [0, 0.5]
    body: |                       <- inline markdown (or: source: markdown/guide/sync.md)
      ## Sync backups

      1. Enable **Sync** in settings.
      2. Copy the seed URL shown below.
      3. Paste it into your notebook's frontmatter.
    ring:
      target: seed-url
  - id: backup-check
    range: [0.5, 1.0]
    body: |
      After ~30s the **Last sync** row updates. If it shows
      `pending` for minutes, see [Troubleshooting](#troubleshooting).
```

Code touch: one pane branch in ScrollRunwaySection (screen === 'doc' → render CanvasProse from body/source instead of EditorWindow), the ring’s “container first child” measurement already works for any element.

Idea C screen: image — screenshot walkthrough of external pages

For “set up your local server / sync backups” guides the subject is an external page that can’t be embedded. A full-bleed screenshot is the pane; the ring addresses a percentage region of it, so the walkthrough survives re-screenshotting.

```scroll
runway: 360vh
screen: image
stages:
  - id: server-repo
    range: [0, 0.33]
    src: assets/guide/server-repo.png
    caption: "Clone the sync server repo and run `bun install`."
    ring:
      region: [4, 62, 92, 26]    <- [x%, y%, w%, h%] of the image
  - id: server-env
    range: [0.33, 0.66]
    src: assets/guide/server-repo.png
    caption: "Copy `.env.example` to `.env` and set `SEED_SECRET`."
    ring:
      region: [4, 30, 60, 14]
  - id: server-run
    range: [0.66, 1.0]
    src: assets/guide/server-running.png
    caption: "`bun run start` — the health check answers on :8787."
```

Code touch: an ImagePane (img + overlay ring positioned by percent), one region: key in ring parsing. Same reproduction story as A/B.

Idea D screen: web — live external page in the pane

When the external tool allows embedding (your own local server, an internal notebook), load it live instead of a screenshot. Sandboxed, same ring model.

```scroll
runway: 300vh
screen: web
stages:
  - id: open-admin
    range: [0, 0.5]
    url: http://localhost:8787/admin
    caption: "The admin panel lists every seed this server serves."
  - id: rotate-seed
    range: [0.5, 1.0]
    url: http://localhost:8787/admin
    caption: "Rotate the seed to invalidate a leaked URL; clients re-sync on next save."
```
Constraint worth stating in the DSL: most third-party sites send X-Frame-Options/CSP frame-ancestors and will refuse to embed. So screen: web realistically covers your own local server and co-operative tools; everything else falls back to Idea C screenshots. The parser should warn (not fail) when a stage mixes url: with an external origin.

Idea E Dynamic steps — conditional and repeated stages

For “syncing with external notebooks/seeds” the path branches per user. Two small additions keep it data-driven instead of hand-authored:

  • when: on a stage — the stage is skipped (its range re-normalized) unless a quest/state flag holds. Flags come from the existing quest ledger (localStorage) or app state, so “you use Obsidian sync” can gate a stage.
  • foreach: on a stage — the stage repeats over a query result (e.g. one stage per external notebook seed the user has configured), each repeat reusing one ring target measured per row.
```scroll
runway: auto                  <- derived from expanded stage count
screen: doc
stages:
  - id: has-sync?
    when: quest:sync-enabled   <- skipped entirely for offline-only users
    range: [0, 0.25]
    body: |
      You have sync on. This guide walks one seed at a time.
  - id: seed-walk
    foreach: query:"list seeds"  <- one expanded stage per seed row
    body: |
      ## Seed {{seed.name}}

      URL: `{{seed.url}}` — last sync {{seed.lastSync}}.
    ring:
      target: seed-url
```

This is the only idea that needs a real data source (a WQL query against app state), so it should land last — A–D are self-contained authoring features.

4. Suggested phasing

PhaseScopeWhy first / why later
1Idea A (ring by data-guide-target) + Idea B (screen: doc)Smallest diff on existing seams (ScrollRing + one pane branch); immediately unblocks prose/component walkthrough guides written entirely in markdown.
2Idea C (screen: image + region:)Covers external pages that refuse embedding; only needs an image pane + percent ring.
3Idea D (screen: web, sandboxed)Nice for your own local server; strictly optional once C exists.
4Idea E (when: / foreach:)Requires a stage-expansion pass over the runway ranges plus a query data source — a runtime feature, not just rendering.

5. Open questions

  • Should data-guide-target also resolve inside the tour’s registered-screen panes, unifying the two targeting models (closed RingTargetKey registry vs. open selector)? Unifying means the tour registry becomes just pre-registered keys.
  • For foreach:, what is the expansion order contract when combined with fixed range: stages — do authored ranges describe pre-expansion or post-expansion progress?
  • Are guide assets (assets/guide/*.png) versioned in the same markdown/canvas corpus, or a parallel asset root? Today resolveSource only reads .md sources.
